# CLEAR 교육 환급 MVP PRD 초안

버전 v0.3 · 2026년 10월 10일 · 2단계 제품 요구사항 · 기술 설계 전

CLEAR는 교육 운영자가 확정한 환급 조건을 외부 기록과 연결하고, 사전에 예치한 지급 재원을 조건에 따라 지급하는 서비스다. 이번 MVP의 핵심 조건은 **TOEIC 총점 800점 이상과 수강률 80% 이상을 모두 충족하는 것**이다. AI는 조건 초안과 근거 확인을 돕고, 자격 판정과 지급에는 확정된 규칙을 적용한다.

장기 적용 대상은 어학원 환급반이다. 먼저 통과할 최소 MVP는 가상 운영자 1곳·환급반 1개·TOEIC·시드 학습 API로 범위를 제한한다. 운영자와 참가자가 조건·예치·기록 확인·지급 상태를 이해할 수 있는 전체 흐름을 우선 완성한다.

이 문서는 개발 지시나 구현 완료 보고가 아니다. 제품 코드와 과거 실험은 변경하지 않았다. 권고안을 초안의 기본 경로로 사용하되 사용자 결정과 구분한다.

목표 시연일은 **2026년 11월 7일**이다. 사용자는 그때 현재 설계한 MVP보다 높은 수준의 결과물을 원한다. 따라서 아래 확정된 MVP는 먼저 통과할 최소 기준이며, 11월 7일 결과물의 상한이 아니다. 11월 7일의 최우선 방향은 운영자와 참가자가 개발자 도움 없이 전체 흐름을 직접 완료하는 제품 완성도다(D15b 확정). 개발에 참여하지 않은 체험자 최소 2명이 운영자·참가자 역할을 나눠 핵심 과업을 독립 완료하는 검증도 필수다(D15c 확정). 목표 시연일은 참가자의 정상 제출·청구 마감일을 뜻하지 않으며, 환급 정책의 실제 날짜는 별도로 정한다.

## 결정 상태

- **확정**: 사용자가 직접 결정했거나 기존 요청에서 명시한 범위.
- **권고 기본안**: 작성자가 자료와 점검 결과를 바탕으로 제안한 초안의 기본 동작. 사용자의 명시적 확정과 구분한다.
- **미확정**: 사용자 권리나 제품 범위에 영향을 주는 선택으로, 아래 결정표에서 답을 받아야 한다. 권고가 있어도 자동으로 확정하지 않는다.
- **기술 설계 이관**: 제품상 동작을 충족할 구체적인 구현 방법. PRD에서 라이브러리·계약 구조를 미리 고정하지 않는다.

## 해결할 문제와 성공 가설

운영자는 환급 조건 안내, 기록 취합, 조건 비교, 중복 확인, 지급 상태 문의를 개별적으로 처리해야 한다. 참가자는 자신에게 적용되는 조건과 기록의 부족한 부분, 예치 여부, 지급 지연 사유를 알기 어렵다. 이 문제를 줄일 수 있다는 것이 제품 가설이며 실제 절감률은 아직 측정하지 않았다.

MVP는 다음 가설을 확인한다.

1. 운영자가 확정한 조건을 참가자 화면·검증 결과·실제 지급에 일관되게 적용할 수 있다.
2. 허용된 디지털 기록에 대해 같은 입력이면 같은 판정과 사유를 제공하고, 정상 지급에 추가 수작업 승인을 요구하지 않을 수 있다.
3. 예치와 지급 권한을 확보한 참가자는 운영자 서비스가 중단된 뒤에도 청구할 수 있다. 발급 이전 장애까지 해결한다는 약속은 아니다.
4. 운영자는 기록 오류·미충족·외부 장애·지급 실패를 구분해 처리할 수 있다.

사업적 효용은 운영자 검토 시간, 재입력 횟수, 상태 문의, 처리 지연을 관찰해 검증한다. ‘업무 80% 감소’, ‘신뢰 비용 0’, ‘100% 진위 보장’ 같은 수치를 실측 없이 주장하지 않는다. 사용자에게 확정받은 수강률 80%와 업무 절감률은 서로 다른 개념이다.

## 멘토링 반영 방향

1차 멘토링에는 서로 다른 적용 대상과 대안이 함께 제시돼 있다. 현재 교육 환급 목표와 이미 구현된 자산에 맞는 내용을 선택적으로 적용한다. 멘토링의 사업·법률·성능 관련 예시를 검증된 사실로 받아들이지 않는다.

| 분쟁·미발급 대응 후순위, 13쪽 | 자동 지급 경로와 오류 사유에 집중. 기록 보완은 허용하되 강제 지급 중재는 제외 | 임의 지급 승인 기능이 규칙 검증을 우회하지 않도록 함 |
| 서버 중단 대응 후순위, 13쪽 | 기존 독립 청구 보장은 보존하고 필수 회귀 검사에 포함 | 이미 있는 자산을 제거할 이유가 없음. 새로운 분산 인프라 전체 구축으로 범위를 확대하지 않음 |
| 승인과 지급 단계 축소, 15쪽 | 정상 자격 판정 후 추가 지급 심사 없음. 참가자의 청구 버튼과 독립 청구는 유지 | 자동 판정과 트랜잭션 제출은 구분. 백그라운드 대납·자동 제출은 후속 선택 |
| OCR·DAO 중재·SBT·숨은 세금 환급 등 다른 확장 제안 | 이번 MVP 제외 | 교육 환급의 현재 목표와 검증 범위를 벗어남 |

## 사용자와 범위

운영자는 조건을 작성·확정하고 예치 상태와 참가자별 검증·지급 현황을 확인한다. 참가자는 조건을 이해하고 지갑을 연결해 신청하며, 기록 검증과 지급 결과를 확인하고 청구한다. CLEAR 검증 서비스는 확정된 규칙을 실행한다. 운영자가 매 신청을 자의적으로 합격 처리하는 심사 역할은 두지 않는 것이 기본안이다.

| 이번 MVP 포함 | 후속 또는 제외 |
| --- | --- |
| 한 반의 정책 작성·검토·확정과 참가자 동의 | 여러 기관 운영, 범용 자유서술 조건 실행 |
| 지갑 소유 확인과 신청 연결, 실명 미검증 표시 | 휴대폰 실명 인증, 실제 학원 회원 DB 연동 |
| 참가자별 예치 상태와 고정 수취인 | 실제 수강료 결제·PG·은행 환불·실자금 |
| TOEIC 응시자·성적 연결 검증 경로 | 사진 OCR 수동 판정, 기타 자격시험 전체 지원 |
| 시드 API의 학습 기록과 수강률 판정 | 실제 학원 LMS 연동 및 실제 수강 사실 입증 |

| 개인정보 비공개 처리와 출처 구분 | 개인 증명의 공개 RPC·공개 체인 제출 |
| 캐시 또는 수동으로 재현 가능한 정책 검토 | 기존 AI 예산 우회, 새로운 유료 AI 평가 실행 |

TOEIC의 세부 종류는 TOEIC Listening & Reading 총점 기준을 권고한다. 인정 기간은 반 운영기간 내 응시로 확정했으며, 복수 응시는 인정 기간 내 최고 총점 적용으로 확정했다(D06b). 허용 시험 종류는 TOEIC Listening & Reading을 기본안으로 둔다(D06c). 실명 본인인증을 제외했으므로 ‘한 사람 한 번’의 강한 보장을 완료했다고 표시하지 않는다.

## 환급 규칙

| 규칙 | 초안 기준 | 상태 |
| --- | --- | --- |
| 점수 충족 | 인정 기간 내 유효하게 검증된 시험의 최고 총점 ≥ 800 | 점수·기간·최고 총점 적용 확정. TOEIC L&R 종류는 D06c 권고 기본안 |
| 수강률 충족 | 수강률 ≥ 80% | 비율·계산 단위·완료 인정 규칙 확정 D03·D07a·D07b |
| 결합 방식 | 두 조건 모두 충족 | 확정 |
| 지급액 | 50 TEST 고정액 1회, 부분 지급 없음 | 권고 기본안 |
| 예치 | 운영자가 해당 신청의 지급액 전액 예치 후 등록 확정 | 권고 기본안 |
| 지급 대상 | 신청 때 동의하고 예치 시 고정한 지갑 | 확정 D11. 예치 후 변경·분실 복구는 후속 |
| 지급 준비 | 유효한 신청·예치·연결된 증빙·두 조건 충족·청구 가능 기간·미정산을 모두 확인 | 제안 요구사항 |
| 부족한 데이터 | 확인 필요 또는 검증 장애. 확정 미충족이나 지급 가능으로 자동 전환하지 않음 | 권고 기본안 |
| 예치금 회수 | 합의된 최종 청구 기한 이후 미정산 몫만 운영자 회수. 지속 장애에도 마감 유지 | 원칙 확정 D08a·D08c. 실제 기한은 D08b 미확정, 회수 실행 방식은 기술 설계 이관 |
| 조건 변경 | 동의·예치된 신청에 소급 변경하지 않음 | 권고 기본안 |

확정된 수강률 계산은 `완료된 필수 강의 수 ÷ 고정된 필수 강의 수`이다. 중복 강의 기록은 한 번만 세고, 분모 0 또는 불완전한 응답은 판정 보류한다. 79.99%를 화면 반올림으로 80%로 보이게 해 합격시키지 않는다. 강의 시간을 분모로 사용하지 않는다. 필수 강의 목록과 완료 기준은 참가자 동의 전에 고정하며, 동의한 신청에 적용되는 목록·기준은 이후 바꾸지 않는다. 시드 학습 API에서 반 운영기간 내 완료로 기록된 필수 강의만 분자에 포함한다(D07b 확정). 기간 밖 완료나 미완료 강의는 제외하고, 완료 여부·시각 등 판정에 필요한 기록이 불완전하면 보류한다. 시드 기록은 실제 시청·수강 사실을 입증한 것으로 표현하지 않는다.

원본 증명의 생성 시각, 시험 응시일, 학습 완료 시각, 데이터 조회 시각, 지급 권한 만료, 청구 마감은 각각 구분한다. 과거 진단 증명은 새 신청의 유효 증명으로 취급하지 않는다. 신선한 조회가 과거 시험을 새 시험으로 바꾸지도 않는다. 인정 기간은 응시일 기준이며, 성적 발표일이나 증명 발급일 기준이 아니다. 반 종료 직전 시험의 성적 발표를 기다릴 수 있는 제출 기간은 D08에서 정한다.

## 대표 사용자 흐름

### 운영자 조건 확정

운영자가 안내문을 입력하거나 제한된 규칙 양식을 직접 작성한다. AI를 사용했다면 초안 값·원문 인용·누락·충돌 질문을 함께 보여 준다. 운영자는 800점·80%를 포함한 지급 조건과 금액·기간·출처·지갑·회수 규칙을 검토한다. 필수 항목이나 충돌이 남아 있으면 정책을 확정할 수 없다.

확정 후 참가자에게 제시할 조건 요약과 버전을 만든다. 사람의 수정은 원문과 구분해 보존한다. 정책을 수정해야 하면 새로운 버전을 만들고 이미 동의한 신청의 조건을 바꾸지 않는다. AI는 실행 코드나 지급 권한을 직접 만들지 않는다.

### 참가자 신청과 예치

참가자는 점수·수강률·인정 기간·지급액·제출 및 청구 기한·미검증 범위를 한 화면에서 확인한다. 지갑을 연결하고 소유 확인과 조건 동의를 진행한다. 신청과 수취 지갑을 고정한 뒤 운영자의 예치가 확인되면 등록 확정으로 표시한다. 동의 전에 수취 주소와 함께 ‘예치 후 지갑 변경 및 분실 복구를 지원하지 않으며, 지갑 접근 권한을 잃어도 다른 지갑으로 대체 지급하지 않는다’는 MVP 제한을 안내한다(D11 확정).

지갑 연결, 동의 서명, 예치 완료는 서로 다른 상태다. 서명만 끝났거나 예치 거래가 대기·실패한 경우 ‘환급 재원 확보’로 표시하지 않는다. 신청 처리 오류로 참가자 키가 서버에 저장돼서는 안 된다.

### 기록 확인과 자격 판정

참가자가 기록 확인을 시작한다. YBM 기록은 허용된 원천·서명·정책·시험 연결·신청 및 지갑 연결·유효 시간을 확인한다. 학습 기록은 시드 API에서 읽고 시드임을 표시한다. 각 조건에 사용한 기록의 종류와 기준 시각을 보여 준다.

점수는 인정 기간 내 유효하게 검증된 시험 중 최고 총점을 사용한다. 선택된 총점과 응시자 정보는 같은 시험 기록으로 연결돼야 하며, 여러 시험의 LC·RC를 조합하지 않는다. 기록이 일부 누락된 경우 확인된 점수가 낮다는 이유만으로 영구 미충족을 확정하지 않고 보완 가능 상태를 유지한다.

두 조건이 모두 충족되고 나머지 신청·예치·기한 요건도 맞으면 지급 준비 단계로 넘어간다. 점수가 부족한 경우 점수 조건 미충족, 수강률이 부족한 경우 수강률 조건 미충족을 구분한다. 데이터 누락·외부 장애·서명 오류는 해당 사유를 보여 주고 합격이나 영구 탈락으로 덮어쓰지 않는다.

### 지급과 직접 청구

기본안은 자격 판정이 완료되면 추가 운영자 심사 없이 청구 자료를 제공하는 것이다. 참가자는 지급액·지갑·마감을 확인하고 청구한다. 거래 제출 직후에는 처리 중으로 표시하며 실제 정산 확인 후 지급 완료로 전환한다. 동일 청구를 반복하거나 동시에 제출해도 두 번 지급되지 않아야 한다.

독립 청구 자료는 참가자가 내려받아 보관할 수 있어야 한다. 자료 발급 이후 운영자와 발급 서비스가 중단돼도 별도 화면에서 같은 권리로 청구할 수 있어야 한다. 반대로 발급 전 중단은 ‘독립 청구 가능’으로 표시하지 않는다. 청구 자료 발급 후 운영자의 지급 취소와 추가 승인 요구는 허용하지 않는다(D09 확정). 오류 확인과 기록 보완은 발급 전에 끝내야 한다. 청구 마감과 자료 유효 기간은 D08 및 기술 설계에서 일치시킨다. 테스트 환경에서는 체험용 가스를 사전에 제공하고 참가자가 자신의 지갑으로 직접 청구하도록 권고한다. 가스 제공량·방식과 부족 시 안내는 기술 설계에서 구체화하며, 청구 시 운영자 서버의 추가 승인이나 실비 결제를 요구하는 방식은 기본안에 포함하지 않는다. 이 보장은 기한 없는 청구나 이미 정산된 권리의 재지급을 뜻하지 않는다.

### 보완과 기한 종료

기록을 다시 조회하거나 보완할 수 있는 동안에는 조건별 상태를 갱신한다. 참가자는 수정된 원천 기록으로 재검증할 수 있지만 화면의 임의 합격 버튼으로 조건을 우회할 수 없다. 운영자도 실패 사유를 볼 수 있으나 확정 규칙을 바꾸거나 임의 지급하는 버튼을 제공하지 않는 것을 권고한다.

외부 기록 조회 장애가 발생하면 정상 제출 마감 이후에도 사전에 고지한 보완 기간 동안 재시도를 허용하며, 이 기간에는 운영자가 예치금을 회수할 수 없다(D08a 확정). 보완 기간은 정책 확정과 참가자 동의 때 안내해야 하며, 장애가 난 뒤 임의로 기한을 바꾸는 방식으로 처리하지 않는다. 보완 완료 후에도 청구할 시간이 남도록 제출·보완·청구 기한을 함께 설계한다.

정상 제출 마감을 T로 두면 보완 종료는 T+3일, 최종 청구 마감은 T+10일이다(D08b 기간 확정). 일 단위 간격은 각각 72시간과 168시간으로 계산하고, 실제 날짜·시각과 표시 시간대는 참가자 동의 전에 정책에 고정한다. 장애가 없어 보완을 적용하지 않더라도 최종 청구 마감은 앞당기지 않는다. 보완 종료 후 7일은 마지막 청구 기회이며, 이미 청구 자료를 발급받은 참가자가 보완 종료까지 기다려야 한다는 뜻은 아니다. 보완 기간은 검증·발급을 마칠 수 있도록 운영하고, 이후 7일을 추가 증빙 제출 기간으로 사용하지 않는다.

정상 제출 기간에 YBM·학습 API의 장애가 서비스 기록으로 확인되면 해당 반의 등록 참가자 모두에게 사전 고지한 보완 기간을 적용한다(D08d 확정). 개별 제출 시도·실패 이력을 요구하지 않으며, 최초 제출 기회를 놓친 등록 참가자도 해당 기간에 제출할 수 있다. 서비스 기록으로 확인된 외부 장애와 개별 조건 미달·잘못된 증명은 구분한다. 장애 확인을 이유로 점수·수강률 요건을 면제하거나 시험·학습 인정 기간과 최종 청구 마감을 바꾸지 않는다.

보완은 기록 조회·제출을 다시 할 기회이며, 확정된 시험 인정 기간이나 학습 활동 기간을 자동 연장하는 것은 아니다. 보완 기간 종료 뒤에도 외부 장애로 검증을 완료하지 못한 신청은 지급 가능으로 전환하지 않는다. 장애가 계속돼도 합의한 최종 청구 마감은 유지하며, 마감 이후 미정산 몫은 운영자가 회수할 수 있다(D08c 확정). 추가 장애 보류나 자동 기한 연장은 MVP에서 지원하지 않는다.

실제로 조건을 달성했어도 기한 내 검증·권한 발급·청구가 완료되지 않으면 지급받지 못할 수 있다는 제한을 참가자 동의 전에 안내한다. 장애로 끝난 신청은 조건 미달과 구분해 ‘검증 미완료로 기한 종료’ 사유를 남긴다. 발급된 청구 자료도 합의한 최종 청구 기한까지만 유효하며, 마감 전 취소 금지(D09)와 마감 이후 회수(D08c)를 구분한다. D08b의 보완 3일·이후 청구 7일은 확정됐으며, 실제 달력 날짜는 아직 미확정이다. 장애 확인에 사용할 서비스 기록 형식과 오류 분류, 회수 실행 방식은 기술 설계에서 정한다.

## 상태와 예외 처리

신청 상태, 기록 검증 상태, 지급 상태를 분리한다. 조건 미충족과 거래 실패는 다른 문제이며, 화면에서 하나의 ‘실패’로 합치지 않는다.

| 구분 | 주요 상태 | 동작 원칙 |
| --- | --- | --- |
| 정책 | 작성 중 → 검토 필요 → 확정 | 미해결 조건은 확정 금지. 동의 후 변경은 새 버전 |
| 신청 | 신청 중 → 동의 완료 → 예치 대기 → 등록 확정 | 예치 확인 없이는 등록 확정 아님 |
| 기록 | 미조회 / 확인 중 / 유효 / 확인 필요 / 검증 장애 / 무효 증빙 | 외부 장애와 변조·출처 오류를 구분 |
| 자격 | 미판정 / 조건 충족 / 조건 미충족 / 판정 보류 | 완료 전 진행률 미달은 현재 미충족이며 기한 전 영구 탈락으로 해석하지 않음 |
| 지급 | 준비 전 → 청구 가능 → 거래 처리 중 → 지급 완료 | 자격 충족만으로 지급 완료 표시 금지 |
| 종료 | 최종 청구 기한 종료 → 회수 가능 → 회수 완료 | 보완 기간 및 최종 마감 전 회수 금지. 최종 마감 이후 미정산 몫만 회수. 지속 장애에도 자동 연장 없음 |

| 상황 | 사용자 표시와 처리 | 하면 안 되는 동작 |
| --- | --- | --- |
| 점수 또는 수강률 부족 | 부족한 조건과 인정 기준 표시, 허용 기간 안에서는 재조회 | 다른 조건이 높다고 보정 지급 |
| 필수 기록 누락·분모 0 | 확인 필요, 부족한 기록 안내 | 누락을 0점 또는 합격으로 임의 변환 |
| YBM·학습 API 장애 | 검증 장애, 마지막 성공 시점과 재시도 안내 | 일시 장애를 최종 자격 박탈로 확정 |
| 증명 변조·미신뢰 출처 | 증빙 거부와 재제출 안내 | 운영자의 합격 버튼으로 우회 |
| 오래된 증명·잘못된 신청 연결 | 새 검증 요구 | freshness나 지갑 연결 검사를 완화해 통과 |
| 지갑 불일치·잘못된 체인 | 올바른 지갑/체인 연결 안내, 거래 차단 | 연결된 다른 지갑으로 자동 지급 |
| 준비금 부족 | 지급 준비 안 됨, 운영자에게 부족 상태 표시 | 지급 보장 또는 완료 표시 |
| 거래 제출 후 응답 유실 | 거래 식별자로 결과 확인, 확인 중 표시 | 무조건 새 지급 권한 발급 |
| 중복·동시 청구 | 같은 신청은 기존 정산 결과 안내, 같은 반의 동일 원천 시험 기록 재지급 차단. 다른 신청의 개인정보는 노출하지 않음 | 신청·지갑 변경이나 증명 재발급으로 우회 |
| 정상 제출 기간의 외부 장애 | 서비스 기록으로 YBM·학습 API 장애 확인 시 해당 반의 등록 참가자 모두 사전 고지한 보완 기간 적용. 개인별 실패 기록 불필요. 보완은 정상 제출 마감 후 3일이며 실제 달력 날짜만 미확정 | 개별 실패 이력이 없다는 이유로 대상 제외, 보완 중 회수, 몰래 기한 연장, 장애를 이유로 자동 합격 |
| 권한 발급 전 서비스 중단 | 발급 미완료·청구 준비 전 | 직접 청구로 해결됐다고 주장 |

## 데이터와 신뢰 경계

| 대상 | 맡기는 책임 | 남는 신뢰 또는 제한 |
| --- | --- | --- |
| AI | 조건 초안·인용·질문 | 일반 정확도나 효용 입증 없음. 자격 판정·지급 권한 없음 |
| 운영자 | 정책 확정·예치·상태 관리 | 정책 의미와 모집 조건 책임. 지급마다 새로운 재량 심사 금지 권고 |
| 검증 서비스 | 허용된 기록 검증·연결·결정적 평가 | 서버 서명 방식이면 서버의 판정과 발급 키를 신뢰함 |
| YBM와 Reclaim | 외부 원천과 공증 서명 | 공식 학원 연동·CLEAR 실명 인증과 동일하지 않음 |
| 시드 API | 모의 학습 기록 | 실제 수강을 보증하지 않음 |
| 계약 | 동의 설정·자금·고정 수취인·권한·기한·일회 정산 | 자연어 의미나 실제 학습 사실을 스스로 판별하지 않음 |

화면에는 ‘실제 YBM 기록’, ‘시드 학습 기록’, ‘합성 시험 데이터’, ‘과거 검증 자료’, ‘저장된 AI 예시’를 각각 명확히 표시한다. 실제 기록과 시드 기록이 함께 사용된 결과를 ‘전 과정 실데이터 검증’이라고 부르지 않는다.

개인정보가 포함된 원본 증명은 AI·공개 RPC·공개 체인에 보내지 않는다. MVP에서 새로 수집한 YBM 원본 증명은 검증과 청구 자료 발급이 완료되면 삭제한다(D12a 확정). 직접 청구에 필요한 자료와 최소 검증 이력은 남기며, 기존 실험의 원본·증명·정책 파일은 이 삭제 정책의 대상이 아니다. 원본을 지운 뒤에는 원문을 다시 대조하는 오류 조사에 제약이 있음을 전제로 한다.

청구 자료가 정상적으로 발급·저장되어 참가자가 확보할 수 있는 상태인지 확인한 후 원본 삭제를 수행해야 한다. 참가자가 원본 재제출이나 서버 재검증 없이 직접 청구할 수 있어야 하며, 원본이 필수인 청구 구조는 이 결정과 양립하지 않는다. 이미 서명된 원본의 개인정보만 지우고 원래 서명이 유효하다고 간주하지 않는다. 개인정보 원본을 포함하지 않는 별도 지급 자료의 형식과 검증 경계는 기술 설계에서 확정한다.

최소 검증 이력은 정책 버전·검증 시각·결과와 사유·지급 권한 및 정산 연결에 필요한 항목으로 제한하는 것을 권고한다. 원본 개인정보를 추출값·디버그 로그·캐시·백업에 복제해 삭제를 무의미하게 만들지 않도록 설계한다. 검증 실패·사용자 중단 등 청구 자료 발급이 끝나지 않은 새 원본은 수집 후 최대 24시간 이내에 삭제한다(D12b 확정). 같은 원본의 재시도·복사로 보관 기한을 다시 시작하지 않는다. 24시간 이내라도 발급이 완료되면 D12a에 따라 삭제한다. 보관 가능 시간과 증명 유효 시간은 별개이며, 만료된 증명은 보관 중이어도 자격 검증에 사용할 수 없다. 원본 삭제 이후 재시도에는 새 증명이 필요하고, 재수집으로 제출·보완·청구 기한이 연장되지는 않는다.

잔여 청구 자료·최소 검증 이력·재사용 방지 정보의 서비스 보관 사본은 최종 청구 마감 후 30일 이내 삭제한다(D12c 확정). 보관 중 참가자는 본인 자료만, 필요한 운영 담당자는 업무에 필요한 최소 이력만 열람할 수 있다. 참가자가 내려받은 사본과 체인에 기록된 거래는 서비스 사본 삭제 대상에서 제외한다. 청구 기한 중 자료 접근과 재사용 방지에 필요한 정보는 유지해야 하며, 30일 보존 상한은 청구 기한 연장을 뜻하지 않는다. 서비스 관리 로그·캐시·백업에 삭제 대상 사본을 남겨 보존 상한을 우회하지 않는다. 삭제 후 원문 조사·자료 재발급에 제약이 있음을 안내한다.

이번 MVP에는 독립 실명 확인이 없으므로 서로 다른 시험 기록을 쓰는 같은 사람을 완전히 식별할 수 없다. 같은 반에서는 동일 원천 시험 기록으로 신청·수취 지갑을 바꾸거나 증명을 재발급받아도 재지급할 수 없다(D10 확정). 단순한 증명 파일 hash가 달라졌다고 새로운 시험으로 취급하지 않는다. 다른 반에서의 재사용 정책과 실명 기반 중복 판별은 후속 과제로 남긴다. 원본 삭제 이후에도 이 보장이 유지되도록 최소한의 재사용 방지 정보를 보관하되 원본 개인정보를 그대로 보관하거나 공개하지 않는 구현은 기술 설계에서 정한다.

MVP의 필수 완료 환경은 로컬 체인이며, 공개 Amoy 지급은 후속 목표다(D13 확정). 필수 시연은 운영자 조건 확정 → 참가자 동의 → 운영자 예치 → 두 조건 확인 → 청구 자료 확보 → 지급 → 중복 시도 차단이다. 별도 짧은 장면으로 ‘검증 장애 시 보류’와 ‘자료 확보 후 서버 중단에도 청구’를 보여 준다.

합성 자료로 통합을 먼저 검증한 뒤, 실제 YBM 증명을 신청·수취 지갑에 연결하고 유효 시간과 확정 조건을 검사해 로컬 지급까지 완료한 사례 최소 1건을 확보해야 MVP 완료로 인정한다(D14a 확정). 과거 저장 증명 재현은 별도 진단이며 이 기준을 충족하지 않는다. 해당 사례의 학습 기록은 시드 API임을 명시한다. 실제 YBM 기록이 인정 시험 기간·800점 조건을 만족하지 않거나 신청 연결·유효 시간 검사를 통과하지 못하면 성공 사례로 세지 않는다. 시연을 위해 조건이나 검증을 완화하지 않으며, 필요한 실제 기록 확보가 안 된 경우 실제 통합 항목은 미완료로 남긴다.

필수 검증 규모는 실제 성적 보유자 1명과 별도의 합성 신청 최소 2개다(D14b 확정). 실제 1명의 신청·지갑 연결과 로컬 지급 성공은 A13, 합성 신청 간 기록·권리·준비금 격리는 A12로 각각 확인한다. 추가 실제 참여자 모집과 다인 운영 검증은 후속이며, 이 결과로 서비스 정원·동시 처리 용량·실사용 성능을 검증했다고 주장하지 않는다.

사용자는 시연에 사용할 수 있는 800점 이상 성적이 이미 있다고 확인했다. 이는 자료 확보에 관한 사용자 응답이며, 실제 점수·응시일·조회 가능 여부나 새 신청 연결 검증이 끝났다는 뜻은 아니다. 개인정보나 성적표는 이번 작성 과정에서 수집하지 않았다.

기존 성적을 활용한 가상 반 시연으로 확정했다(D14c). 해당 응시일을 포함하는 가상 반 운영기간을 시연 정책에 미리 명시하고, 동의·예치·새 증명 검증·청구는 개발 시점에 실행한다. 증명 생성 시각이나 시험일을 조작하거나, 검증 결과를 본 뒤 동의한 정책을 바꾸지 않는다. 제출·보완·최종 청구 기한은 실제 실행 시점에 맞춰 정한다. 이 시연은 과거 실제 성적과 시드 학습 기록을 연결한 기술 검증이며, 사전 가입·학습·응시를 거친 실제 환급반 운영 실적은 아니다. D06a의 시험일 포함 검사와 A13의 새 증명·신청 연결·유효 시간 검사는 그대로 적용한다.

공개 Amoy 지급은 MVP 완료의 필수 조건에 포함하지 않는다. 완료 보고에는 실제 YBM 기록·시드 학습 기록·로컬 지급의 조합임을 명시하고 녹화·캐시·실시간 화면을 구분한다. 새 로그인·증명 생성 등 실행은 해당 개발 단계에서 별도로 진행하며, 이번 PRD 결정으로 지금 실행하지 않는다.

AI 사용성은 운영자가 원문과 초안의 오류를 찾는지, 누락을 보완하는지, 잘못된 조건을 승인하는지로 관찰한다. 시간 절감과 도입 의향은 동일 과업의 수동 기준 및 실제 참여자 피드백이 확보된 뒤 평가한다. 인터뷰 인원·성능 목표는 후속 평가 계획에서 정하고 수치를 미리 성과로 쓰지 않는다.

## 11월 7일 목표와 최소 MVP 이후 범위

D15a에 따라 목표 시연일은 2026년 11월 7일이며, 현재 확정된 자격·지급·개인정보·장애 정책과 A01–A18을 최소 기준으로 유지한다. 실제 성적 보유자 1명과 합성 신청 최소 2개는 초기 검증 규모다. 더 높은 목표를 정하더라도 이미 합의한 권리와 검증 기준을 낮추지 않는다.

D15b에 따라 11월 7일의 최우선 목표는 운영자와 참가자가 개발자의 구두 설명·터미널 조작·수동 데이터 수정 없이 조건 확정·신청·예치·증명 제출·지급을 완료하고, 보류 사유를 이해해 재시도하거나 보관 자료로 독립 청구할 수 있는 제품 완성도다. 환경 준비와 테스트 데이터 설정은 사전에 수행하되, 과업 도중 개발자가 개입해 성공시킨 사례를 독립 완료로 세지 않는다. 사용자가 읽는 안내와 오류 설명은 제품 안에서 제공한다.
