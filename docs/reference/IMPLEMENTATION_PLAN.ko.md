# CLEAR 11월 7일까지의 단계별 구현 계획

2026년 10월 10일 · [3단계 기술 설계](DESIGN.ko.md) 기준 · 모든 시각은 일정 설명상 한국 시간

**10월 21일까지 실제 YBM 연결과 로컬 지급을 완성하고, 10월 27일까지 각자 PC에서 사용할 수 있는 테스트 사이트를 준비한 뒤, 11월 2일까지 처음 쓰는 체험자 검증을 진행한다.** 11월 3–6일은 발견된 문제 수정과 재검증에 쓰고 11월 7일에 결과를 보여준다. 공개 Amoy·실제 LMS·신규 유료 AI 기능은 이 경로의 선행 조건으로 넣지 않는다.

이 날짜는 구현 착수 이후의 권고 목표다. 10월 11일에 구현을 시작할 수 있고 주 담당 구현자 1명이 집중해 작업한다는 가정이다. 실제 가용 시간은 확인되지 않았으며 일정 보장은 아니다. 이번 요청에서는 문서만 작성했고, 구현·배포·외부 실행은 시작하지 않았다. 별도 작업자나 체험자를 확보했다고 가정하지 않는다.

## 단계별 모델과 추론 수준

앞으로 이 프로젝트의 단계 시작·전환 안내와 작업 계획에 **추천 모델 · 추론 수준 · 선택 이유**를 항상 표시한다. 추천은 실제 실행 설정과 구분하며, 모델을 자동으로 전환했다고 표현하지 않는다. 이는 개발을 돕는 Codex 설정이며 제품 내부 AI 모델이나 기존 유료 AI 호출 예산을 변경하는 결정이 아니다.

기본 개발 설정은 GPT-6.1 Sol + high다. 아키텍처·서명·지급 권리·동시성·개인정보 경계처럼 오류 비용이 큰 작업은 GPT-6 Astra + high, 명확한 화면·문구·시험 결과 정리는 GPT-6.1 Sol + medium을 권고한다. 아래는 CLEAR의 작업 위험도에 맞춘 작성자 권고이며 모델 간 실측 비교 결과가 아니다.

| 기존 단계 | 추천 모델 | 추론 | 선택 이유 |
| --- | --- | --- | --- |
| 1단계 기존 구현 점검 | GPT-6.1 Sol | high | 코드·저장 기록·제약을 연결해 확인 |
| 2단계 PRD 작성·변경 | GPT-6.1 Sol | high | 권리·범위·예외 규칙의 일관성 유지 |
| 3단계 기술 설계·중요 변경 검토 | GPT-6 Astra | high | 신뢰 경계·계약·증명·보관 정책을 함께 판단 |

medium은 일반 작업의 균형점, high는 복잡한 설계·디버깅에 우선 적용한다. high에서도 가설이 충돌하거나 계약 불변식·재사용 공격·복구 경계 검토가 반복해서 막힐 때만 해당 작업을 xhigh 후보로 올리고, 추가 결함 발견이나 통과 기준 개선이 있는지 비교한다. max·ultra는 일상 기본값으로 두지 않는다. 단순 문구·레이아웃 수정은 Sol medium으로 충분한지 먼저 확인한다.

공식 안내는 Sol을 시간·비용도 고려하는 복잡한 작업, Astra를 깊은 분석에 적합한 선택으로 설명한다. 높은 추론은 더 많은 시간·사용량을 쓸 수 있으므로 통과 기준을 충족하는 가장 가벼운 설정을 유지한다. 모델·추론 선택은 테스트와 사용자 검증을 대체하지 않는다. [공식 모델 선택 안내](https://developers.openai.com/api/docs/guides/model-selection), [추론 수준 안내](https://developers.openai.com/api/docs/guides/reasoning)

다음 작업 안내 예시는 ‘P1 기술 확인 — 추천: GPT-6 Astra / high. 이유: YBM 문맥·신청 지갑 결합과 외부 증명 경로를 먼저 확인’이다. 다만 W01 작업본 준비만 수행하는 턴이라면 GPT-6.1 Sol / medium을 표시한다. 현재 앱에 노출된 식별자는 GPT-6.1 Sol=gpt-6.1-sol, GPT-6 Astra=gpt-6-astra이며, 가용 옵션이 달라지면 새로 확인한다.

핵심 의존 경로는 W02 → W08 → W09 → W12와 W07 → W10 → W14 → W15다. 실제 증명 생성과 원격 복구를 마지막 주에 몰지 않는다. 실제 원천이 막혀도 정책·합성 평가기·계약 구현은 진행할 수 있으나 실제 연결 항목을 완료로 바꾸지는 않는다.

목표 시연일 11월 7일을 자동으로 claimUntil에 넣지 않는다. 예를 들어 정상 제출 마감을 11월 7일 18:00 KST로 잡는다면 보완 종료는 11월 10일, 최종 청구 마감은 11월 17일 같은 시각이다. 이는 산술 예시이며 채택된 일정이 아니다. 이런 정책을 택하면 11월 7일 이후에도 권리와 복구 경로를 유지해야 하고, 잔여 서비스 자료 삭제 상한은 12월 17일이다.

반대로 만료·회수를 11월 7일 당일 보여주려고 실제 반의 동의한 마감을 당기지 않는다. 기간 경계 시연은 별도 합성 환경의 가상 시계 결과로 제시한다. 실제 운영 반과 다른 환경임을 표시한다.

## 일정이 밀릴 때의 우선순위

1. 자격·신청·지갑·기간·중복·준비금·개인정보 오류를 먼저 해결한다. 화면이 성공처럼 보이는 것으로 대체하지 않는다.
2. 정상 과업·재시도·독립 청구와 처음 쓰는 사람의 검증을 유지한다. 화면 장식, 부가 통계, 지원 브라우저 확대, AI live 분석은 뒤로 미룬다.
3. 공개 Amoy 지급, 실제 LMS, 다기관, 실명 인증, 가스 대납, 모바일, wallet 복구는 필수 일정에 끼워 넣지 않는다.
4. 필수 기술 연결이 실패하면 사용자와 범위·일정 변경을 결정한다. 800점·80%·freshness·지갑 연결을 완화하거나 실제 증명을 합성으로 치환하지 않는다.

## 구현 착수 순서

다음 실제 개발 요청이 오면 W01부터 시작한다. 이후 W02의 YBM 연결 가능성을 조기에 확인하면서 W03–W05의 독립적인 합성 작업을 진행한다. 첫 기능 완료 단위는 새 정책을 동의한 두 합성 신청의 예치·자격·지급이며, 그다음 실제 증명과 독립 청구를 연결한다.

현재 작성한 것은 3단계 설계와 실행 가능한 작업 순서다. 자동으로 11월 7일까지 작업을 예약하거나 지속 실행하도록 설정하지 않았으며, 제품 코드를 수정하지 않았다.
