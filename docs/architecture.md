# 아키텍처

이 문서는 v4의 목표 설계를 요약합니다. [구현 상태](status.md)와 [상세 설계](reference/DESIGN.ko.md)를 구분해서 읽으세요.

## 기술별 역할

| 계층 | 역할 | 책임의 한계 |
| --- | --- | --- |
| AI 조건 보조 | 안내문에서 초안·원문 근거·확인 질문 생성 | 사람이 승인하며 AI에 지급 권한을 부여하지 않음 |
| 증명 수집 | YBM 응답을 Reclaim 증명으로 확보 | 원천 데이터·공증자·인증 세션에 대한 신뢰가 남음 |
| 검증·판정 서버 | 출처·서명·신청·지갑·시험 연결 및 고정 조건 검사 | 올바른 자격 판정과 발급을 신뢰해야 함 |
| 학습 기록 어댑터 | 고정된 필수 강의 기준에 따라 완료율 집계 | 이번에는 시드 자료. 학원 API와 정확성 검증은 후속 |
| 스마트컨트랙트 | 예치 재원·고정 수취인·지급 권한·기한·중복 지급 통제 | 외부 성적이 사실인지 다시 검증하는 기본안은 아님 |
| 직접 청구 화면 | 확정된 권리를 가진 참가자가 기한 내 청구 | 계약·RPC·지갑의 접근성과 가스가 필요 |

## 왜 블록체인인가

DB도 규칙 저장과 중복 차단을 할 수 있습니다. CLEAR가 검증하려는 차이는 **지급 권한이 계약에 확정된 후 운영자나 CLEAR의 추가 승인 없이 참가자가 청구할 수 있는가**입니다.

이를 위해 규칙·실행 설정에 대한 동의, 재원 예치, 취소 불가능한 권한 확정, 고정 수취인, 직접 청구 경로를 함께 설계합니다. 자격 발급 전 서버의 오판정·발급 거부까지 해결하지 않으며, 최종 기한 후 미정산 재원은 회수할 수 있습니다. 로컬 체인은 기능 시연이므로 운영자 통제를 제거했다고 주장하지 않습니다.

## 증명과 개인정보

v4는 성적 원문을 체인 밖에서 검증하고 불투명 식별자·중복 방지값·최소 지급 권한을 계약에 등록하는 설계입니다. 과거 단일 공증자 서명 검증 성공을 다중 공증이나 신청자 실명 확인으로 확대하지 않습니다.

과거 YBM 진단 경로를 v4로 옮기려면 임시 증명 키와 수취 지갑의 연결, 서명 문맥, TEE 호환성, 클라이언트 격리, 원본 삭제를 확인해야 합니다. [경로 설계](w02/V4_ROUTE_DESIGN.ko.md)
