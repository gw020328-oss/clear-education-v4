## 3. 카드별 — 1차 기준 통과 여부

| 카드 | 흐름 | 확인한 범위 |
| --- | --- | --- |
| 강의 수강 | 「강의 열기」 → Moodle 대역 완료 → 복귀 → **확인 중 · 재확인 요청 접수(op-…)** → 5초 뒤 **새 판정 확정 · 충족** + 완료 상태·완료 기록 | 합성 대역에서 끝까지 확인. 실제 Moodle·서버는 A·C 연결 뒤 |
| 과제 제출 | 「과제 열기」 → 제출 → 복귀 → 접수 → 확정 · 제출 상태·제출 기록 | 같은 틀. 합성 확인 |
| 회고 | 「회고 쓰기」 → 글 올림 → 복귀 → 접수 → AI 검토 승인 대기 → 검토 중 → **AI 검토 완료 · 미충족** + 판정 사유 + **다시 쓸 곳 · 회고 게시판 — 보충할 항목: 배운 점** + 버튼 「회고 다시 쓰기」 → 고쳐 올림 → 복귀 → 다시 요청 → 충족 | 합성 확인. 검토 중엔 다시 쓰라고 하지 않는다 |
| HackerRank | 「인증 시작」 → 「메시지 읽기」 → 서명할 메시지 표시 → 「서명」 → HackerRank 창 → **검증 중 · 서버 검증 대기** + 「다시 진행」 → 동의 → 복귀 → **서버 검증 완료** | 합성 확인. 창을 닫거나 취소하면 「다시 진행」 으로 창만 다시 연다. 다시 서명하지 않는다 |

공통: 돌아왔다는 사실이나 접수만으로는 충족으로 바꾸지 않는다. 바꾸는 건 서버 조건 줄의
지문(state·current·evidenceId·evidenceRevision·reasonCode) 변화뿐이다.

## 4. 실제로 붙인 부분 / 합성인 부분

- **실제로 붙인 것은 없다.** 카드는 기존 읽기 API(조회·판정 근거)와 기존 driver 의
  인증 동작(bind·approval·sign)만 부르던 그대로이고, 거기에 **재확인 요청 포트 하나**를 더했다.
  포트 모양은 검증표(11/5)에 적힌 A 의 `POST /bootcamp/v4/applications/:id/source-refresh`
  응답과 같다. 주소는 코드에 넣지 않았다. 호스트가 `createConditionCards({ refresh })` 로 끼운다.
- 합성: `demo-server.js` 의 재확인 대역, `standin.js` 의 Moodle·HackerRank 대역 탭.
  화면에 「시연 데이터」 라고 적힌다.

```js
// 호스트가 끼우는 모양 (controller.js)
createConditionCards({
  refresh: async ({ criterionId, expectedRevision }) => /* A 의 source-refresh */ ({
    status: 'QUEUED' | 'RATE_LIMITED' | 'RECORDED' | 'UNAVAILABLE',
    operationId, retryAfterSeconds,
  }),  // null 을 돌려주면 "이 빌드엔 경로 없음" — 지금 develop 과 같다
  certificate: { start, read, sign, resume },  // resume: 로그인 창 다시 열기
});
```

## 5. A·C 가 제공해야 할 값

**A**
1. `source-refresh` — 검증표대로 `{ criterionId, expectedRevision }` → `{ status, operationId, retryAfterSeconds }`.
   화면은 네 status 를 모두 다르게 보여준다. 강의만 먼저 와도 된다(과제·회고는 `UNAVAILABLE` 로 답하면
   카드가 「아직 확인할 수 없어요」 로 둔다).
2. 접수 뒤 **새 판정이 확정되면** 그 조건 줄의 `evidenceId` 또는 `evidenceRevision` 이 바뀌어야 한다.
   그래야 카드가 '확정' 으로 읽는다. 바뀌지 않으면 "접수됐지만 미확정" 으로 남는다.
3. 회고: 고쳐 올린 글에 대해 재확인 요청이 오면 AI 승인(`aiApproval`)을 다시 발급하는지.
   카드는 승인 대기·검토 중을 세션 `phase`·`aiApproval` 로 읽는다(기존과 같음).
4. HackerRank **다시 진행** — 서명 뒤 로그인 창을 닫았을 때 호스트가 창을 다시 여는 동작(`resume`).
   없으면 카드 버튼이 '호스트 동작 미제공' 으로 잠긴다. 다시 서명시키지 않는다.
5. HackerRank 로그인 완료·수집 중을 세션에서 구분하는 필드(검증표 A-4). 지금은 '검증 중' 하나로만 보인다.

**C**
1. Moodle 탭의 카드 복귀 때 `refresh-activity`(→ A 의 source-refresh)를 `read` 앞에 부르는 연결(검증표 C-1).
   카드 쪽은 `refresh` 포트에 그 결과를 넘기면 된다.
2. 링크는 새 탭으로. 같은 탭이면 복귀 추적이 사라진다(검증표 C-3). 카드는 `target=_blank` 로 그린다.
3. `conditionTargets` 에 과제·회고 cmId(검증표 A-3·C-2). 없으면 「과제 열기 · 주소 미제공」 으로 잠긴다.

## 7. 오규원 11/5 답 반영

> 강의부터 실제 연결. 과제·회고는 값이 오기 전 미연결 표시. QUEUED 만으로 충족·확정 표시 금지.
> expectedRevision 은 **명령의 기준이 되는 신청 개정 번호**, evidenceRevision 은 조건 근거 갱신 확인값.
> 신청 전체 개정이나 다른 조건의 근거 변화를 이 카드의 새 판정으로 읽지 말 것. 상태가 같아도 유효한
> 새 근거가 확인됐으면 재확인 완료로 표시 가능. 고친 회고의 지난 AI 결과를 새 글 결과처럼 보이지 말 것.
> HackerRank 「다시 진행」 은 기존 요청·서명이 유효할 때로 한정, 만료·취소·계정 변경이면 서버가 허용하는
> 다음 절차. resume 포트 전까지 비활성 유지. 접근 환경은 본부 확인 뒤 통보. HackerRank 로그인은
> 실행 담당 Mac 의 관리형 브라우저라 터널로 Moodle 만 열어도 따로 확인 필요.

반영한 것:

- `expectedRevision` 을 **신청(판정) 개정 번호**로 보낸다(`controller.js` 의 `getRevision` → 화면이 가진
  `decision.revision`). 전에는 조건 근거 번호를 넣고 있었다 — 고쳤다.
- 카드의 '확정' 판단은 그대로 **그 조건 줄의 지문**만 본다(state·current·evidenceId·evidenceRevision·reasonCode).
  신청 전체 개정 번호나 다른 조건의 근거는 지문에 없어 반영으로 읽지 않는다.
- 새 근거는 왔는데 판정 상태가 같으면 **「재확인 완료 · 서버가 새 근거를 확인했어요 · 판정은 그대로 미충족」**.
  상태가 바뀌었을 때만 「새 판정 확정」.
- 회고: 고치러 갔다 돌아와 아직 새 판정이 안 온 동안은 **「지난 글의 검토 결과 · 미충족 — 고친 글은 아직 검토 전」**
  으로 적고 항목 목록에 '지난 글 기준' 표시, 「회고 다시 쓰기」 는 그동안 내리지 않는다(다시 쓰라고 하지 않음).
  새 입력의 승인·검토 상태는 A 가 주는 `phase`·`aiApproval` 로 그대로 표시한다.
- HackerRank 「다시 진행」: `resume` 포트 없으면 비활성 유지. 유효 범위 한정은 **A 의 값이 필요**하다 —
  아래 5절에 추가.

A 에 추가로 필요한 값:
- HackerRank 기존 요청·서명의 **유효 여부**(유효 / 만료 / 취소 / 계정 변경)와, 무효일 때 서버가 허용하는
  다음 절차 이름. 카드는 유효할 때만 「다시 진행」 을 열고, 아니면 그 절차의 버튼을 보여 준다.

## 8. 11/5 밤 화면 점검에서 고친 것 (11/6, 같은 가지)

학생처럼 네 카드를 끝까지 눌러 보고(강의 → 과제 → 회고 미충족 → 고침 → HackerRank 4/4) 찾은 것.
오규원이 올린 수정 4개(d610d32·6f38da6·140fed7·407b036) 위에 얹었다. 시험 462 통과.

- **늦은 판정 보류** (f37b9e7). 회고를 "배운 점 빼고" 올리고 판정 전에 고쳐 올린 뒤 돌아오면,
  지난 글의 미충족이 이번 방문의 요청과 겹쳐 도착해 「새 판정 확정 · 미충족 · 다시 쓰세요」 로
  닫히고 고친 글은 다시 안 읽혔다. 이제 **이번 방문의 재확인 요청이 처리 전**(미요청·QUEUED·
  RATE_LIMITED)이면 바뀐 판정을 보류(`held`)하고, 같은 회차에 한 번 더 물어 **RECORDED** 면 그
  자리에서 확정한다. 근거(evidenceId) 없는 줄로 바뀐 것(승인 대기·검토 중)은 중간 단계라 계속 읽는다.
  재확인 경로가 없으면(지금 develop) 전처럼 바로 확정. 문구: 「확인 중 · 서버 판정이 바뀌었지만
  이번 재확인 요청은 아직 처리 전이에요 · 지난 요청의 결과일 수 있어…」.
  **전제(A)**: `source-refresh` 가 처리 뒤 재요청에 `RECORDED` 를 답한다(11/5 답의 값). 늘 QUEUED 만
  주면 보류가 안 풀려 약 2분 뒤 「판정은 바뀌었지만 처리 확인 못 함」 STALLED 로 멈춘다.
  오규원 시험 '늦은 최종 조회' 의 요청 횟수 기대값을 모드별 2/3 으로 바꿨다(확정 확인 1회가 더 간다).
- **카드 버튼을 안 거친 경우** (5d8eda2). Moodle 에서 직접 제출하고 CLEAR 를 열면 카드가 떠난
  기록이 없어 다시 읽지 않았고 「다시 확인」 도 없었다. 미충족 카드(HackerRank 제외)에 안내 한 줄과
  「다시 확인」 을 항상 두고, `recheck` 가 방문 없이도 새 방문을 만들어 요청한다(`departed:false` —
  회고 카드가 "고친 글" 이라 하지 않음). 「새 판정 확정」 뒤에도 미충족이면 「다시 확인」 유지.
- **4/4 뒤 안내**. 「네 조건을 모두 충족했어요. 이 화면에서 더 할 일은 없어요. 100 TEST 지급은
  기존 지급 흐름에서 서버가 처리하고, 결과는 기존 CLEAR 화면(수령 확인)에서 보여요.」 지급됐다고
  말하지 않는다.
- **대역**: 이미 기록된 강의·과제 대역 페이지는 제출 버튼 대신 기록 시각과 「다시 확인」 안내.

확인한 것(결함 아님): 재확인 경로 없음 모드는 37초 뒤 「자동 재조회 멈춤 · 다시 확인」, 미지원 모드는
「아직 확인할 수 없어요」, 폰 너비(375px) 가로 넘침 없음. 서버 반영 지연이 5초 제한보다 짧으면 정상
경로에서도 보류 문구가 몇 초 보였다가 확정된다 — 틀린 표시는 아니다.
