# 학생 환급 조건 카드 — 원래 화면 이동과 복귀 후 판정 갱신

2026-11-05. 작성: 학생 화면 병렬 작업(Claude). 받는 사람: 본부(오규원), A(백엔드·지급), C(Moodle 화면·플러그인), D(연결 상태 패널).

학생이 환급 조건 카드에서 원래 화면(Moodle 강의·과제·회고, HackerRank 인증)으로 가서 할 일을
마치고 CLEAR 탭으로 돌아오면, 별도 증빙 업로드 없이 서버 판정을 다시 읽어 보여 주는 작업이다.
**돌아왔다는 사실만으로 충족으로 바꾸지 않는다.** 판정은 서버 줄의 `state` 만 말한다.

## 3. 구현 (작업 브랜치)

새 디렉터리 `web/src/bootcamp/condition-return/` — 지문 대상이 아닌 파일만이다.

| 파일 | 역할 |
| --- | --- |
| `targets.js` | 이동 정보 계약 `clear-student-condition-targets.1` 제안과 검사. 주소는 문자열로 받지 않고 origin·module·cmId 조각으로 받아 조립한다(https, 로컬 Moodle 만 http). 없으면 버튼을 잠근다 |
| `tracker.js` | 떠날 때 그 조건 줄의 지문(state·current·evidenceId·evidenceRevision·reasonCode)을 남기고, `visibilitychange`·`pageshow`·`focus` 로 돌아오면 기존 조회로 다시 읽는다. 바뀌면 반영됨, 그대로면 확인 중 → 3·7·15·30·60초 재조회 → 멈춤(「다시 확인」). 가려진 탭에서는 묻지 않는다. 같은 탭 왕복은 sessionStorage(30분)로 기억한다 |
| `evidence.js` | 조건 줄(`view.criteria`, 절차 준비 전이면 `operations.evidence.criteria`)과 판정 근거(`decisionEvidence`) — 지금 판정과 같은 판정의 근거만 쓴다(live-evidence.js 와 같은 기준) |
| `status.js` | 카드 문구. 강의·과제의 Moodle 기록, 회고의 AI 검토 단계·사유·원문 위치, 인증서의 Reclaim 단계·서버 검증 결과 |
| `cards.js` | 네 카드. 기존 `.cc` 뼈대와 `criteria.js` 의 `CRITERIA`·`displayState`·`collectionFrom` 을 그대로 쓴다. 「자세히」 는 기존 `onOpen` 을 부른다 |
| `controller.js` | 호스트가 몇 줄로 붙이는 입구 `createConditionCards({ getState, read, loadEvidence, targets, certificate, onOpen, onChange })` |
| `cards.css` | 새 줄의 스타일. `web/styles.css` 는 지문 대상이라 고치지 않았다. 제품 빌드가 `web/src` 를 복사하므로 여기 둔다. 제품 CSP(`style-src-attr 'none'`)에 맞춰 인라인 스타일이 없다 |
| `demo-server.js` · `preview.js` · `standin.js` | 독립 프리뷰의 **시연용 대역**. 제품 진입점에서 import 하지 않는다 |

쓰는 API 는 기존 것뿐이다 — 읽기 `GET /bootcamp/v4/session`, `GET /bootcamp/v3/applications/:id/procedure`,
`GET /bootcamp/v2/applications/:id/operations`(driver.readLive 가 부르는 그대로),
`GET /bootcamp/v3/applications/:id/decision-evidence/:decisionId`, 쓰기는 기존 driver 의
`bind`(POST source-session)·`approval`(GET source-signature)·`sign`(POST source-signature) 만이다.

## 4. 네 카드 — 실제 연결 / 시연 확인 / 남은 부분

| 카드 | 실제 경로로 연결한 것 | 시연 데이터로만 확인한 것 | 남은 것 (막는 순) |
| --- | --- | --- | --- |
| 강의 수강 | 이동 버튼(서버 이동 정보가 오면 `/mod/page/view.php?id=cmId` 를 새 탭으로), 복귀 감지, 기존 GET 재조회와 지문 비교, 판정 근거의 `completionState`·`sourceCompletedAt`, 확인 중·반영됨·멈춤·읽기 실패 문구, 「자세히」 | 완료 → 서버 재수집 → 충족 반영 | ① 이동 정보 미제공 → 지금은 버튼이 「주소 미제공」 으로 잠김 (A1·C2) ② 원천 재조회 없음 → 돌아와도 「확인 중」 뒤 「아직 반영되지 않았어요」 (A2) |

| 회고 | 이동 버튼(`/mod/forum/post.php?forum=instanceId`, 없으면 `view.php?id=cmId`), 세션 `phase`·`aiApproval` 로 「AI 검토 승인 대기」·「AI 가 회고를 검토하고 있어요」, 판정 근거 `checks.topics` 의 항목별 상태와 UTF-16 원문 위치, 사유는 서버 `reasonCode` 우선·없으면 서버 항목 상태로. 원문은 지어내지 않고 「원문 조회 API 미제공」 이라 적음 | 원문 문장 강조, 「배운 점 빼고 제출」 → 미충족과 사유. 판정기는 AI 가 아니라 예문 문장 포함 여부만 보는 시연 판정기 | ① 이동 정보 (A1·C2) ② 재조회 + 입력마다 AI 승인 재발급 (A2) ③ 원문 조회 API(선택, 기존 한계 `originalTextHttpAvailable:false`) |
| HackerRank 인증서 | 기존 driver `bind` → `approval` → 서명할 메시지를 카드에 그대로 보여 준 뒤 `sign`. 서명 표시를 신청별로 저장(30분)해 같은 탭으로 다녀와 새로 떠도 **다시 서명하라고 하지 않음**. 복귀 재조회, 판정 근거 `verification`(원천 상태·본인 결합·요청 결합·무결성·신선도)·`checks`(인증서·발급 상태·취득 시각). 서버 줄이 MET 일 때만 「서버 검증 완료」 | 대역 탭에서 로그인·증명 동의 → 검증 완료 | ① 통합 브랜치 재봉인(본부) ② 세션에 서명 접수 상태 필드(권장, A3) — 다른 기기·저장소 차단 시에도 재서명 방지 ③ 900초 신선도 만료 뒤 재인증을 서버가 다시 열어 주는 경로 |

공통으로 지키는 것은 `web/tests/condition-return.test.mjs` 24개 시험이 막는다 — 돌아온 것만으로 충족 금지,
판정이 그대로인데 반영됨 금지, 다른 조건 변화를 이 조건 반영으로 읽기 금지, 현재 판정이 아닌 응답·다른 신청
응답 무시, 서버가 준 적 없는 주소·다른 사이트·다른 신청·엉뚱한 모듈로 이동 금지, 서명 전 메시지 표시,
서명만으로 검증 완료 금지, 원문 지어내기 금지, 가려진 탭 조회 금지·겹친 복귀 신호 1회 조회, 같은 탭 왕복
기억·오래된 기록 폐기, 「자세히」 유지.

## 8. A 에 요청 (화면을 막는 것만)

1. **이동 정보 필드** — `GET /bootcamp/v4/session` 응답(참가자일 때)에 `conditionTargets` 를 더해 주세요.
   적용 위치: `tools/bootcamp/live-context.mjs` 의 `getSession` 반환 객체. 값은 이미 호스트 비공개 매핑에
   있습니다(`mapping.courseId`, `mapping.targets.activity.cmId`, `mapping.targets.assignment.cmId`,
   `mapping.targets.reflection.cmId`·`forumId`). 학생이 여는 Moodle origin 만 추가로 필요합니다.
   `normal-client.mjs` 의 `session()` 은 모르는 필드를 그대로 넘기므로 클라이언트 변경은 없습니다.
   통합 브랜치는 `driver.snapshot().bootstrap?.conditionTargets` 를 읽습니다.

   ```json
   {
     "version": "clear-student-condition-targets.1",
     "applicationId": "<현재 신청>",
     "moodleOrigin": "https://<학생이 여는 Moodle>",
     "courseId": 12,
     "targets": [
       { "criterionId": "activity-complete", "cmId": 2101, "module": "page", "name": "1주차 · 파이썬 시작하기" },
       { "criterionId": "assignment-submitted", "cmId": 2105, "module": "assign", "name": "실습 과제" },
       { "criterionId": "reflection-topics", "cmId": 2107, "module": "forum", "instanceId": 31, "name": "회고 게시판" }
     ]
   }
   ```
   허용 모듈: 강의 `page·url·resource·book·lesson·h5pactivity`, 과제 `assign`, 회고 `forum`. 조건당 하나(활동 여러 개는 11/4 합의대로 후속).

2. **원천 재조회** — 지금 수집은 한 번뿐이고(`normal-source-sequence.mjs` 의 `BC_LIVE_SINGLE_COLLECTION`),
   GET 조회는 저장된 판정만 읽습니다(10/29 답변과 같음). 그래서 학생이 Moodle 에서 마치고 돌아와도 판정이 바뀌지
   않습니다 — 화면은 「확인 중」 뒤 「아직 반영되지 않았어요」 를 정직하게 보여 줄 뿐입니다. 필요한 것 중 하나:
   - (가) 참가자가 부를 수 있는 제한된 재조회 명령. 예 `POST /bootcamp/v4/applications/:id/source-refresh`
     `{ criterionId, expectedRevision }` + `Idempotency-Key` → `{ status: 'QUEUED'|'NOT_ALLOWED'|'RATE_LIMITED', operationId, retryAfterSeconds }`.
     세 Moodle 조건만. 회고는 입력마다 기존 AI 승인(`aiApproval`)을 다시 발급. 반영되면 그 조건의 `evidenceId`·`evidenceRevision` 이 바뀌어야 화면이 반영으로 읽습니다.
   - (나) Moodle 이벤트(C 요청 3)를 받아 호스트가 그 조건만 다시 수집.

   화면 쪽 연결 위치: (가)라면 `controller.js` 의 `read` 직전에 한 번 부르는 `refresh` 포트를 더하면 됩니다(지금은 없음 — 존재하지 않는 API 를 부르지 않았습니다).
   참고: 지금 흐름은 수집 시점에 네 조건이 모두 MET 이어야 진행합니다. 오늘 시험에서는 학생이 수집 **전에** Moodle 항목을 마쳐야 합니다.

3. (권장, 막지 않음) **서명 접수 상태** — 세션에 `sourceSignature: { status: 'AWAITING'|'ACCEPTED'|'COLLECTING'|'FAILED', approvalId }`.
   지금은 화면이 서명 표시를 sessionStorage 에 둡니다. 다른 기기·저장소 차단 환경에서도 재서명을 막으려면 서버 값이 필요합니다.

4. **재봉인** — 7 의 두 파일.

## 9. C 에 요청

1. **Moodle 탭에서 무엇을 보여 줄지 결정** — 네이티브 템플릿(`course_refund.mustache`)이 네 카드를 직접 그릴지,
   「환급 확인」 이 팀 학생 화면(이 카드)을 열지. 네이티브로 간다면 `tracker.js` 는 프레임워크 없는 순수 로직이라
   AMD 모듈로 옮겨 쓸 수 있습니다(복귀 신호·지문 비교·제한 재조회·저장).
2. **매핑 공급** — `configure.php`(`classes/form/mapping.php`)에 저장된 조건별 cmId 를 A 가 1 의 모양으로 낼 수 있게
   넘기거나, 네이티브라면 `moodle_url('/mod/'.$modname.'/view.php', ['id' => $cmid])`(회고는
   `/mod/forum/post.php?forum=<instance>`)로 같은 규칙의 링크를 그려 주세요.
3. **완료 이벤트** — `course_module_completion_updated`, `assessable_submitted`, 게시판 `post_created` 를 받아 A 의
   재조회(8-2 나)로 넘기는 관찰자. 별도 업로드 없이 돌아오면 바뀌는 흐름의 정공법입니다.

## 10. D 에 공유

PR #160 C 화면(연결 상태)은 그대로 앞에 두고, 정상 연결 뒤 기존 흐름의 조건 구역이 이 카드가 됩니다.
두 화면 모두 「서버가 말한 것만 완료」 원칙이라 문구가 충돌하지 않습니다.

## 11. 알려진 한계

- 제품 팀 화면은 `pagehide` 에서 자동 조회를 멈춥니다(기존 동작). 같은 탭으로 나갔다가 bfcache 로 되돌아오면 기존
  화면 전체가 멈춘 상태일 수 있어, 카드 링크는 새 탭(`target=_blank`, `noopener`)으로 엽니다.
- 학생 화면이 여러 탭이면 각 탭이 자기 복귀만 추적합니다.
- 프리뷰의 시연 판정기·지연 반영은 실서버 동작이 아닙니다. 화면에 「시연 데이터」 라고 적었습니다.
