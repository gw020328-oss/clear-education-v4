# 학생 환급 조건 카드 4종 — 실제 Moodle 시연·검증표

2026-11-05. 시연 담당·A·C 가 같은 표로 통과 여부를 적는다. 제품 코드·Moodle 환경은 이 문서로 바꾸지 않는다.

**기준** — 카드: PR #163 `05918d9`(`web/src/bootcamp/condition-return/`). Moodle 플러그인 0.1.21 후보: C 로컬 `codex/moodle-native-clear-ui` `bffb450`
(카드를 `build_condition_panels.sh` 로 `05918d9` 에서 번들, origin 미푸시). 원천 재조회: A 로컬 `codex/native-activity-return` `1e2240c`(진행 중, 0.1.21 과 별도 줄기).

**표시** — `[P]` 합성 프리뷰(`web/condition-cards.html`)에서 확인 가능 · `[M]` 실제 Moodle + 호스트에서만 확인 · ⚠ **A·C 확인 필요**

## 0. 두 경우를 섞지 않는다

| | **S. 저장 판정 재표시** | **R. 원천 재조회로 판정 갱신** |
| --- | --- | --- |
| 무엇을 부르나 | 복귀 시 GET 만: 0.1.21 은 `read-application`(→ `/bootcamp/v3/…/procedure`)·`decision-evidence` | 위 + `POST /bootcamp/v4/applications/:id/source-refresh` `{criterionId, expectedRevision}`(A `1e2240c`, **강의 수강만**) → `QUEUED`·`RATE_LIMITED(5초)`·`RECORDED`·`UNAVAILABLE` |
| 0.1.21 상태 | 붙어 있음 | ⚠ 카드 복귀 흐름에서 `refresh-activity` 를 부르지 않음(C-1) |
| 카드 기대 표시 | 학생이 Moodle 에서 마쳐도 판정 그대로 → 「확인 중」 → 「아직 반영되지 않았어요」. **이게 정상이다** | 새 근거가 기록되면 「서버 판정이 바뀌었어요 · 지금 판정 충족」, 카드가 충족 모양으로 |
| 구분하는 근거 | 조건 줄의 `evidenceId`·`evidenceRevision` 이 떠나기 전과 같다 | `evidenceId` 또는 `evidenceRevision` 이 바뀌고, 판정 근거의 `source.acquiredAt` 이 학생이 Moodle 에서 마친 시각 이후다 |

카드는 조건 줄 지문(state·current·evidenceId·evidenceRevision·reasonCode)이 바뀔 때만 「반영됨」 이라 한다. 돌아온 사실, 다른 조건의 변화, `decision.current:false` 응답은 반영으로 치지 않는다.

## 4. A·C 확인 필요

**A**
1. 원천 재조회 범위 — `1e2240c` 는 강의 수강만(`activityReturnOnly`, 강좌 2·cmId 3 고정). 과제·회고 재조회와 회고의 입력별 AI 승인 재발급 계획.
2. `activityReturnOnly` 처럼 절차 준비 전에도 `read-application`(procedure)이 읽히는지. 안 읽히면 0.1.21 카드는 「최신 판정을 읽지 못했어요」(0.1.21 은 operations 를 넘기지 않음).
3. `conditionTargets` 에 과제·회고 대상 추가 시점과 `name` 문구.
4. HackerRank 로그인 완료·수집 중·서명 접수를 세션에서 구분하는 필드.
5. 통과 값 목록 — `completionState`·`submissionState`·topics `state`·`verification` 다섯 값.
6. 자체 공증(`selfAttestor`) 근거를 카드에서 공식 검증과 다르게 표시할지.
7. 회고 근거의 모델·루브릭·프롬프트 버전(현재 `UNAVAILABLE`)과 원문 위치 기준 텍스트.
8. `source-refresh` 의 `QUEUED`·`RATE_LIMITED`·`UNAVAILABLE` 를 카드 문구로 보여 줄지.

**C**
1. 0.1.21 카드 복귀 시 `refresh-activity` 호출 연결(`course_native_workflow.js` 의 `read` 앞) — 없으면 실제 Moodle 시연은 S 경우만 된다.
2. HackerRank 카드 버튼 — 인증 동작(`certificate`)을 넘길지. 넘긴다면 `approve-source-signature` 성공 뒤 `markSigned()` 호출로 재서명 유도를 막아야 함.
3. 메모리 저장 사용 — 링크가 항상 새 탭으로 열리는지(같은 탭이면 복귀 추적 사라짐).
4. 「자세히」 가 판정 헤딩으로 스크롤만 하는 것(기존 근거 상세 아님)이 의도인지.
5. 대상 필터(`moodleOrigin`·`courseId` 일치)가 실제 시연 강좌 값과 맞는지.
6. 지정 항목 설정 — 페이지 완료 조건(열람 자동/수동), 과제 「제출 버튼 필요」, 회고 게시판 형식. 학생 할 일 문구가 이 값에 달려 있다.
7. 0.1.21 브랜치(`bffb450`) origin 푸시 시점 — 검증표 기준 커밋 고정용.
