| 출처 | 내용 |

| Q&A | "커리큘럼 내 1회 가량 기수별 오프라인 네트워킹 세션" (불참 가능) |

**출석체크가 주 1회**라서 조건 7의 "1~10주차 9회 이상"은 **주 1회 × 10주 중 9회**라는 뜻입니다.

### 안내문 안의 불일치 — F3가 잡아야 할 자리

```
배너     "15주 집중 과정"
조건 7   "1~10주차동안 9회 이상 출석"      → 10주차까지
조건 5   "각 주차 별로 부여된 수업 …"      → 몇 주차까지인지 안 적혀 있음
```

과정은 15주인데 출석 판정은 10주차까지고, **수강 완료 판정 주차는 명시가 없습니다.**
YBM 안내문의 L36/L78 충돌과 같은 패턴 — AI가 한쪽으로 단정하면 안 되고 `HELD`로 잡습니다.

> ⚠ **수강 완료 판정 주차** — 비어 있음
> "「15주 집중 과정」과 「1~10주차 출석」이 함께 있고, 조건 5는 주차 수가 적혀 있지 않습니다.
> 몇 주차까지입니까?"

**데모에서 주차를 줄이지 않습니다.** 조건은 안내문 그대로 두고, 불일치는 불일치로 살려둡니다.
시간만 압축해서 보여주면 됩니다.

### 금액 계산과 지급 방식

```
실결제금액 2,490,000
− PG사 수수료 (요율 미기재)   ← 안내문에 % 가 없음 = F3의 HELD 필드
− 제세공과금 22%
= 환급액
```

조건 11 + **"환급은 최초 결제 시 사용한 동일한 결제 수단으로 처리됩니다"** →
계좌 송금이 아니라 **PG 결제 취소**입니다. PG 수수료가 공제되는 이유가 여기 있고,
12개월 할부면 할부 취소로 처리됩니다. **쿠폰·포인트 사용 불가**는 실결제금액을 깨끗하게
유지하려는 장치입니다.

→ 시연에서는 이걸 **TEST 토큰 지갑 송금**으로 보여줍니다. 결제 취소 대기도 통장 사본 제출도 없습니다.

단, **실제 도입에서 결제수단 환급을 지갑 송금으로 그냥 대체할 수는 없습니다.** 계약·정산·세무
절차가 따로 있습니다. 시연(TEST)과 실제 PG·정산 도입은 구분합니다.

**공개 자료 없음**: 환급 신청 절차·서류·입금 시점은 어디에도 공개돼 있지 않습니다.
참고로 같은 회사의 기업교육은 "환급 신청 이후 3~4주 내 입금"이라고 안내합니다.

## 1-5. 포지셔닝 — 시연은 메타코드, 상용은 소규모 부트캠프 전체

메타코드는 **하나의 예시**입니다. 같은 조건을 가진 곳이 팔 곳입니다.

```
공통점   직원 10명 안팎 · 기수당 20~50명 · 비국비 자비 · 환급을 모집 수단으로 씀
문제     조건 수십 개 × 수십 명 × 수십 주차를 사람이 세는 것 말고 방법이 없음
         자체 검수 시스템을 만들 돈도 인력도 없음
→ CLEAR  검수 자동화 + 판정 근거 공개 + 조건 충족 시 자동 지급
```

**확장 경로**

1. **소규모 환급형 부트캠프** (메타코드형) — 조건이 공개돼 있고 기수가 작아 도입 리스크가 낮음. 첫 레퍼런스
2. **환급을 하고 싶지만 못 하는 소규모 운영자** — 독립 크리에이터 유료 챌린지, 1인 강사 기수제 과정.
   **"있는 비용을 깎는다"가 아니라 "못 하던 상품을 가능하게 한다"**
3. **대학 비교과·학생회 보증금, 온라인 챌린지(DAO)** — 멘토가 거론한 나머지 두 갈래. 판정 구조가 같아 그대로 확장

**대형(YBM·시원스쿨·패스트캠퍼스)은 타겟이 아닙니다.** 미달성이 수익이라 도입 동기가 없습니다.

# 2. 시스템 구성

### 우리가 만드는 것 — 화면 2개

| | 누가 보나 | 무엇을 하나 |
|---|---|---|
| **참가자 화면** | 수강생 (모바일) | 오늘 할 일 · 증빙 업로드 · 조건 현황 · 환급 신청 |
| **운영자 화면** | 메타코드 직원 (데스크톱) | 안내문 → 조건 추출 · 자동처리 현황 · 재원/Circuit Breaker · 건별 판정 근거 |

### 가져다 쓰는 것 — LMS 1개

| | |
|---|---|
| **Moodle** | 강의·출석·과제·퀴즈 기록이 쌓이는 곳. **새로 만들지 않고 띄워서 씁니다** |

```
Moodle ──기록──▶ CLEAR ──판정──▶ 스마트컨트랙트 ──송금──▶ 참가자 지갑
  (LMS)          (화면 2개)                              
```

## 2-1. LMS — Moodle을 그대로 씁니다

메타코드 LMS를 **Moodle로 재현**합니다. 오규원이 이미 실제 재생 → 저장 → 인증 API → 하루 학습
판정까지 검증했습니다(PR 52·56). 여기서 나오는 것:

- 주차별 수강 완료 여부 (해당 주차 내)
- Live 스터디 참석
- 과제·퀴즈 제출 기록과 점수
- 출석 일수

### "모듈"은 LMS와 다른 얘기입니다

**모듈 = LMS 안의 구성 단위.** Moodle 용어로 activity module — 강의 하나, 과제 하나, 퀴즈 하나가
각각 모듈입니다. **LMS가 건물이면 모듈은 방 하나**입니다.

1·2회차 멘토링의 *"참가자 화면을 Moodle 안에 박아서 보여주면 됩니다"* 는 **우리 환급 신청 화면을
Moodle 모듈(플러그인)로 만들라**는 뜻이었습니다. 건물 안에 방을 하나 내라는 것입니다.

**그 방법은 포기했습니다.** `src/dev/server.mjs:76`에 `frame-ancestors 'none'`이 걸려 있어
iframe 삽입이 막히고, 풀려면 보안 헤더를 약화시켜야 합니다.
**다만 iframe 삽입이 막힌 것과 플러그인을 못 만드는 것은 다른 얘기입니다.**
MVP 는 별도 화면·링크로 가고, Moodle 플러그인·LTI 연동은 후속으로 검토합니다.

→ **대신 Moodle에 링크만 걸고 별도 화면으로 띄웁니다.** 건물 옆에 별관을 세우고 복도로 잇는 쪽입니다.

# 4. 전체 흐름

```
1. 참가자가 조건 달성
   Moodle에서 3주차 강의 수강 완료 + 작업형 과제 제출
   (개인 블로그 후기는 수료 후 본인이 작성)

2. AI가 판독
   ├ Moodle API 조회       → 주차 내 수강 완료 ✓, 출석 7/10 ✓
   ├ 코드 계산             → 제출률 100% ✓, 퀴즈 정답률 84% ✓ (기준 80%)
   ├ LLM 채점              → 작업형 과제 정답률 92% ✓ (기준 90%)
   ├ Vision 판독           → 천재지변 서류 읽힘 ✓
   └ Reclaim 공증          → 개인 블로그 글 게시 확인 ✓

   ※ 못 읽으면 지어내지 않고 "보완 필요"로 참가자에게 돌려보냄

3. 판독 결과를 오라클을 통해 스마트컨트랙트에 전달
   사실(공증) + 판단(서명)을 분리해서 전달
   신청 ID · 정책 버전 · 증거 버전 · 금액 · 수령인 · 만료를 함께 서명

4. 컨트랙트가 즉시 송금
   사전 예치된 풀에서 참가자 지갑으로 TEST 토큰
   releaseRefund(userAddress) — 사람의 건별 승인 없음
   중복 청구·타인 자료는 거절

5. 잔고 부족 시 — 멈추는 것은 "추가 지급"뿐입니다

   TEST 확정 시연: 신청 2건 × 100 TEST = 200 필요 / 금고 초기 150
     ├ 1건째 → 100 전액 배정 → 지급
     └ 2건째 → 남은 50으로 배정 불가 → 대기열
   추가 50 충전 → 2건째 배정 → 지급

   잔액 < 임계치
     ├ 이미 전액 배정된 권리   → 그대로 지급. 막지 않음
     └ 아직 배정 안 된 신규 건 → 대기열. 충전 후 순서대로 배정
   운영자: "긴급 충전 필요 — 부족액 S원 · 대기 M건"
   참가자: "학원 자금 충전 대기 중 · 대기열 3번"
   → 멈추거나 에러 내지 않고 투명하게 대기열 관리

   ※ 전체를 멈추면 이미 자기 몫이 잡혀 있는 참가자까지 못 받습니다.
     우리가 새 미지급을 만드는 셈이고, 프로젝트 취지가 그 자리에서 깨집니다.
     멘토 Q5 원문도 "추가 지급을 일시 정지" 이고, 우선 검증 사항이
     "기존 직접 청구 경로가 훼손되지 않고" 입니다.
     부족액은 오규원 회계값의 S = max(0, U − A) 를 씁니다.
```

# 5. 예치율

> **2026-10-22 정정**: 20% 는 **기수 예산 가정**이고, **신청별 지급은 전액 배정**입니다.
> 두 층이 섞여 있었습니다.
>
> ```
> 층 1  기수 예산     운영자가 기수 시작 때 금고에 얼마 넣나   → 20% (고객 시나리오 가정)
> 층 2  신청별 배정   한 사람 지급을 확정할 때 얼마 잡나       → 그 사람 몫 100% 전액
> ```
>
> 오규원 원문: *"예시의 20%는 **기수 예산 가정**이며 신청별 지급 가능 여부가 아니다"* ·
> *"전체 준비금이 부분 예치일 수 있어도, **개별 지급권리를 확정할 때는 그 금액 전부가 확보돼야 한다**"*
>
> **확정 TEST 정책의 초기 예치율은 20%가 아닙니다.** 정상 시연은 신청별 **100 TEST 전액 배정**,
> 부족 시연은 100 TEST 두 신청에 **초기 150 + 추가 50** 입니다.
> 아래 20% 계산은 **고객 도입 시 기수 예산을 얼마로 잡나** 의 답으로만 남깁니다.

## 먼저 — 완주(수료) ≠ 환급

둘을 구분해야 합니다. 안내문이 명시합니다:

> **"위 환급 기준 미달 시 환급가능 대상자에서 제외됩니다."**

```
완주 / 수료   과정을 끝까지 들은 것
환급          조건 1~9를 "전부" 충족한 것
```

완주해도 환급을 못 받는 경우:
- 퀴즈 정답률 **79%** (기준 80%)
- 작업형 과제 정답률 **89%** (기준 90%) — 단 조건 4로 **1회는 면제**
- 수료 후 **블로그 후기를 안 씀** (조건 9)
- 만족도 조사 미제출 (조건 8)
- Live 스터디 **1회 결석** (참석률 100% 요구)

**메타코드가 홍보하는 완주율이 높더라도 환급률은 그보다 낮습니다.**
두 숫자를 섞으면 예치 계산이 틀립니다.

## 계산

```
총결제액      20명 × 2,490,000 = 4,980만원
예치 20%                       =   996만원   ← 결제 직후 즉시 Lock-up (멘토: 하드코딩)

1인당 재원    2,490,000 − PG 3%(74,700) = 2,415,300원
              (학생 1,883,934 + 원천징수 531,366 — 원천징수분도 재원에 포함)

996만 ÷ 241.5만 = 4.1명 → 20명 중 4.1명 = 환급률 20.6%까지 커버
```

멘토 공식(예상 환급률 15% + 버퍼 5% = 20%)과 맞습니다.

## 환급률이 더 높으면?

| 환급률 | 환급 인원 | 필요 재원 | 필요 예치율 |
|---|---|---|---|
| 20% | 4명 | 966만 | 19.4% |
| 30% | 6명 | 1,449만 | 29.1% |
| 50% | 10명 | 2,415만 | 48.5% |
| 100% | 20명 | 4,831만 | **97.0%** |

환급률이 100%면 예치도 사실상 전액이 필요합니다. **이게 멘토가 지적한 바로 그 문제** —
환급률이 높으면 학원이 예치를 못 견딥니다.

## 그래도 20%를 유지합니다

실제 환급률은 비공개라 모릅니다. 그런데 멘토는 **부족이 나는 것을 전제**하고 그 처리를 보라고 했습니다.

> **Q5 답변**: 최우선 검증 사항은 "자금 부족 상황 발생 시, CLEAR 시스템이 멈추거나 기존 직접 청구
> 경로가 훼손되지 않고 **투명하게 대기열(Queue)을 관리하며** 플랫폼의 신뢰를 유지하는가"임
>
> **전략 3**: 예치율은 **20%로 하드코딩**하고, 컨트랙트 잔액이 환급 요청액보다 적어지는 순간
> 시스템이 일시 정지(Circuit Breaker)

**예치 20%는 "환급을 전부 덮는 금액"이 아니라 "지급을 시작할 수 있는 최소 재원"입니다.**
부족하면 충전하고, 충전 전까지는 투명하게 대기열. 그게 설계이고 멘토가 보고 싶어 하는 것입니다.

다만 **20% 를 제품 상수로 박지 않습니다.** 실제 의무·지급액·달성 분포가 미확인이고
멘토도 "시연 설계용 가정"이라고 했습니다. **설정값으로 두고 시연 가정임을 화면에 표시**합니다
(`METACODE_DEMO_ASSUMPTIONS`).

환급률이 실제로 높다면 **Circuit Breaker가 더 자주, 더 자연스럽게 터집니다.**
데모에는 오히려 유리합니다 — **5명째가 달성하는 순간** 발동합니다.
