### 시연 순서 (11/4 결정)

```
운영자: CLEAR 로그인(메타마스크) → B 안내문 → 조건 구조화 → A 조건마다 읽을 Moodle 항목 지정 → 저장
참가자: Moodle 「환급 확인」 → 기존 구글 로그인 → C 연결 상태(본인·강좌·신청) → 수령인 등록부터 기존 흐름
```

- A 의 칸은 **B 가 찾은 조건을 따라간다.** ① 예문이면 활동·과제 두 칸, ③ 이면 세 칸.
  HackerRank 는 Moodle 칸이 없어 "여기서 고르지 않음" 한 줄로 빠진다.
- C 를 로그인 **뒤**에 둔 이유: 본인 연결(Moodle 학생 ↔ CLEAR 참가자)은 누가
  로그인했는지 알아야 서버가 대조할 수 있다. 로그인 전에 "본인 연결됨" 을 보여주면
  서버가 모르는 것을 보여주는 셈이다.

### 각 화면이 다루는 상태

- **B**: 입력 전·처리 중·완료·조건 구체화 필요·미지원·실패·만료·입력 변경(stale).
  읽기 제안은 "N개 조건을 찾았습니다 — 맞나요?" 로 묻고, 출석률·정답률·참석률·(선택) 은
  "확인하지 않는 것" 으로 따로, 나머지 문장은 접는다. 제안자는 규칙 기반(출처 표시)이고
  Gemini 제안자는 같은 모양 `{id,label,propose(text)}` 으로 끼우면 된다.
  ③ 도구 카드에 '읽는 조건'·'선택 근거(모델이 고른 것 아님)', ③과 ④ 사이에 도구별 실행 상태.
- **A**: 저장된 설정 있음 · 미설정 · 목록이 바뀌어 저장 항목 사라짐 · 항목 없음 ·
  플러그인 미연결 · 저장 실패. 저장 중엔 버튼·칸 잠금(중복 클릭 차단). 선택지는 서버
  목록에서 모듈 종류로 거른 것만(회고 칸에 퀴즈 없음). 수강 활동은 **여러 개 = 모두 완료**.
- **C**: 정상 연결 · 연결 확인 중 · 연결 실패 · 잘못된 강좌 · 세션 만료 · 신청 없음.
  기존 화면 링크는 정상 연결에서만 열림. 만료는 「다시 확인」 없이 Moodle 에서 다시 들어오라고만.
  6단계(로그인·지갑·수령인 등록·조건·동의·지급)는 서버가 말한 것만 '완료', 수령인 등록은
  어느 시나리오에서도 완료가 아님.

## 6. 백엔드에 필요한 것 (우선순위 순)

1. **활동 완료 조건이 대상 여러 개(AND)를 받아야 한다.** 실제 메타코드 안내문이
   "주차별 수업 100% 수강" 이라 1주차·2주차를 다 골라야 하는데, 지금 `clear-core` 의
   조건은 `target` 하나다. A 는 `activity: [2101, 2102]` 로 보낸다. 받기 전까지 화면이
   "서버 미반영" 을 적는다.
2. **운영자 강좌 연결 계약** — 읽기: 플러그인 연결 상태, 연결된 강좌(id·이름·기수),
   항목 목록(`cmId`·`module`·`name`)과 목록 revision, 저장된 매핑. 쓰기: 매핑 + 어느
   목록 revision 기준인지(`basedOnItemsRevision`). 화면 view-model 은
   `course-link-fixtures.js` 의 `clear-operator-course-link-view.1` 참고(서버 DTO 아님).
   미정: 부분 저장(초안) 허용 여부. 지금은 칸을 다 골라야 저장.
3. **참가자 연결 계약** — 로그인한 참가자 기준 Moodle 학생 ↔ 참가자 대조 결과,
   강좌 연결 여부, 신청 존재 여부, Moodle 에서 넘어온 세션 유효 여부. 주소의 강좌/학생
   번호는 표시만 하고 인증엔 쓰지 않는다. view-model 은 `entry-fixtures.js` 의
   `clear-participant-entry-view.1`.
4. **Gemini 제안 호스트 포트** — 입력 안내문 원문, 출력 조항별 `{원문 구절, capability|null}`.
   받으면 `ai-compare.js` 의 `proposer` 만 갈아끼운다. 확인 화면·출석률 문지기·15조합
   fixture·시험은 그대로.
5. Moodle 버튼이 C 를 여는 주소와 토큰(또는 티켓) 전달 방식. 프론트는 주소 번호를
   인증에 쓰지 않으므로 서버 검증 결과만 있으면 된다.

## 9. 오규원 11/4 답 반영

> 화면 분리와 제안자 교체 방식은 그대로. 참가자 연결은 A·C 의 현재 Moodle 인증 계약에
> 맞추고, 운영자 강좌 설정은 기존 플러그인 설정을 재사용. 미지원 조건은 '확인 안 하는 것'
> 대신 '자동 검증 미지원 — 정책 확정 전 처리 필요' 로 표시하고, 미지원이 남은 상태에서
> 전체 환급 정책을 실행 가능으로 표시하지 말 것. 활동 다중 선택은 화면 구조 유지, 실제
> 연결은 활동 하나로 정상 흐름 먼저, 전체 완료 검증은 추가. Gemini 제안은 기존 코어의
> 원문 위치·지원 상태·확인 질문까지 포함한 계약을 받아 화면용으로 변환. API 주소·필드는
> 본부에서 전달.

반영한 것:

- **B 문구** — 출석률·정답률·참석률 묶음 제목을 '자동 검증 미지원 — 정책 확정 전 처리
  필요 · N개' 로, 각 줄 설명도 같은 뜻으로 바꿨다. (선택) 항목만 "환급 조건이 아님" 으로
  남겼다. 선택 사항은 미지원이 아니라 조건 자체가 아니어서다.
- **B 실행 가능 표시 차단** — 미지원 조건이 남은 채 구조화하면 결과 위에 "자동 검증 미지원
  조건 N개가 남아 있어 전체 환급 정책을 실행 가능으로 보지 않습니다" 경고가 붙고, 성공
  배너도 '지원 조건만 쪼갰습니다' 로 바뀐다. 미지원 조항은 구조화에 넘기지 않으므로
  ④ 결과는 지원 조건에 대한 것이고, 그 사실을 화면이 매번 적는다.
- **A 문구** — 활동 여러 개 선택 시 "실제 연결은 먼저 활동 하나로, 전체 완료 검증은 그
  다음" 으로. 화면 구조(체크박스)는 유지.
- **C** — 연결 계약은 A·C 의 현재 Moodle 인증 계약을 따른다. 본부가 필드를 주면
  `entry-fixtures.js` 의 view-model 로 변환하는 `run` 만 쓴다. 화면은 그대로.
- **A 저장 경로** — 기존 플러그인 설정 재사용. 화면의 '저장' 은 그 설정을 쓰는 호출로
  바뀌며, 계약이 오면 `save` 어댑터의 `run` 에 끼운다.

다음 할 일(계약 도착 뒤):

- Gemini 제안 → 화면 변환기. 코어 계약이 주는 **원문 위치·지원 상태(지원/미지원/확인
  질문)·확인 질문**을 `normalize.js` 의 제안 모양 `{clauses[{original, capability,
  notOurs, note}], kept, canonicalText}` 으로 바꾼다. 확인 질문은 접힌 '읽지 않은 문장'
  이 아니라 **묻는 줄**로 따로 보여야 한다. 지금은 필드가 없어 쓰지 않았다.
