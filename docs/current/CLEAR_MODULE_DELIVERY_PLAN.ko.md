## 패키지와 통합 기준

- 하나의 버전 패키지에 조건·계획, Moodle/HackerRank Reclaim 증빙, 회고 AI·근거, 기존 정산 연결 모듈을 둔다. 독립 예제, 설정 예시, 설치·실행 명령을 제공하고 깨끗한 폴더에서 설치·실행한다. 마지막에는 같은 버전으로 제품 회귀를 확인한다.
- 기존 구현을 재사용한다. 새 서명·정책·동의·컨트랙트 의미 변경, 임의 사이트 자동 연동, RAG/LangGraph 전환, 공개 레지스트리 발행은 범위 밖이다. source pin과 검증기 manifest는 유지한다.
- A 기존 Privy 세션은 PR139와 core web 정상 흐름을 담당한다. B는 `src/agent-preview`, `packages/clear-core`, `examples/clear-core` 등 독립 경로에서 AI·모듈을 담당한다. C는 `src/operational-metrics`와 전용 시험·문서를 담당한다. D는 독립 비교·운영효과 패널과 표시 상태, 리허설을 담당한다.
- B/C의 기존 core, web, 루트 패키지, CI, 정본 계획 변경은 본부가 통합한다. D의 core web·라우트·main 연결은 A와 파일별 인계 후 진행한다. 본부가 공통 기준 SHA와 병합 순서를 관리한다. 이번 승인에는 개별 PR 병합이나 공개 배포가 포함되지 않는다.
- 첫 인수에서 B/C가 각각 DTO 예제와 검증을 제공하고 본부가 필드·버전을 확정한다. 비교 DTO는 조건, 네 기능 매핑, 근거 참조, 부족·애매함 보류 사유와 출처 구분을 담는다. 계측 DTO는 조건·신청 분모, 자동 처리 논리 건수, 서버 처리 구간, 오류·재시도, 사람 개입을 구분한다. 확정 전 UI는 어댑터와 명시적 합성 fixture를 사용한다.
- 필수 양측 동의와 예외 수동 검토, 사람의 실작업과 대기를 분리한다. 기존 r2-ledger는 서버 구간만 기록하며 baselineComparable=false, humanWorkReductionPercent=null이다. 동일 사례 비교가 없으면 절감률은 N/A다. 150건·70% 등 예시를 실적으로 표시하지 않는다.
- 실제 모드에서 예시 명단과 자동 합성 fallback을 사용하지 않는다. 공개 합성 근거 시연과 실제 S4 hash/location을 구분하고 개인 원문 API는 추가하지 않는다.
- 기존 증거에서 수령인·금액 변조, 만료, 이전 판정·해시, 중복 지급 거부를 대조한다. 이미 배정된 온체인 권리의 서버 중단 후 별도 청구는 지갑·RPC·가스까지 시험 범위를 명시한다.

## 사용자 접근과 개발자 연동

- 사용자 접근은 준비된 서비스의 브라우저 화면에서 로그인·검토·서명·결과를 확인하는 경로다. 원격 서비스에 접속할 수 있다는 사실은 그 사용자의 OS에서 로컬 수집기를 실행할 수 있다는 뜻이 아니다.
- 개발자 연동은 문서화한 제품 API와 최소 샘플을 자신의 프론트/서비스에서 사용하는 경로다. 내부 관리·평가·체인 쓰기 API를 전부 공개하지 않는다. 지원 origin, 인증·역할·CSRF, wallet/chain 결합, 요청·오류 DTO, 멱등/UNKNOWN 복구, 기한·재사용 방지 계약을 명시한다.
- 범용 모듈을 목표로 정책/프로필, origin/포트, 체인·계약, 원천 대상과 서비스 위치를 검증된 설정으로 분리한다. 특정 반, 계정, 개발자 Mac 절대 경로를 공용 제품 계약으로 고정하지 않는다. 현재 예제의 고정값은 지원 범위와 함께 예제로 표시한다.

의존성 목록은 공개 준비 시 실제 설치 명령과 잠금 파일에 대조한다. 현재 내부 작업본/형제 디렉터리에만 있는 필수 구성은 배포 가능한 소유 소스 또는 설치 절차로 제공하기 전까지 독립 재현 차단 항목으로 기록한다.

## 다른 컴퓨터 인수 절차와 증거

1. 릴리스/커밋, OS·CPU, 브라우저, 런타임과 외부 서비스 버전을 기록하고 빈 작업 경로에서 문서대로 설치한다. 공개 자료에 없는 구두 설명이 필요하면 문서 결함으로 남긴다.
2. 비밀값 없는 샘플로 합성 설치 점검·API 연동을 먼저 수행한다. 실제 서비스/수집 경로는 따로 구분하고 해당 사용자의 계정·키·CA·origin과 격리 환경을 준비한다.
3. 승인된 범위에서 신청부터 지급 결과 조회까지 실행한다. 요청의 공개 식별자·정책/자산 지문·역할·상태·안전 오류 코드·TEST 영수증을 대조하고 중복 요청·만료·재시작 경계를 확인한다.
4. 명령/검사 결과, 화면 단계, 실패와 해결 절차, 외부 지원이 필요했던 부분을 비밀값 제거 후 남긴다. 원문 증명·쿠키·토큰·개인키·회고 본문은 결과 증거로 공개하지 않는다.
5. 합성, 실제 원천, 자체/공식 공증, 로컬 TEST, 공개 테스트넷, 실자산을 별도 결과 칸으로 평가한다. 일부 성공을 전체 제품 완료로 합산하지 않는다.

기존 실행의 코드/자산/증거/승인 기록을 보존하며, 코드 교체를 위한 hotpatch·기한 자동 연장·동의 복사·재사용 방지 완화는 하지 않는다. 현재 오류 수정 적용에는 새 코드 실행이 필요하고 실제 재시험 여부와 사용자 단계는 본부가 조율한다.

작업 모델은 AGENTS 기준으로 선택한다. 서명·권한·자금 경계 검토는 Astra/High를 권장하고, 일반 API/패키징 구현은 Sol/Medium, 단순 문서·상태 갱신은 Sol/Low를 권장한다. 추천과 실제 실행 설정을 구분하며 설정 변경만을 위해 새 세션을 만들지 않는다.
