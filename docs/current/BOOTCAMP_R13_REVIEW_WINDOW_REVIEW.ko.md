# r13 만료 분석과 v22 검토시간 조정

2026-10-24. r13의 기록된 안전 메타데이터와 현재 코드만 검토했다. 실제 증명·원문·응답 본문·인증 비밀은 읽거나 옮기지 않았다. r12는 로그인 대기 중 취소로 끝났으며 취소의 발신 원인은 기록되지 않았다. r13의 만료 문제와 구분한다.

## 확인된 시간

아래 시각은 KST다. 파일 수정시각은 해당 기록의 완료 관측이며 모든 내부 단계의 시작을 증명하지 않는다.

| 관측 | 시각 | 의미 |
| --- | --- | --- |
| HR 수집 완료 | 약 14:42:50 | 실제 계정·인증서 검증 완료 |
| 활동 / 과제 취득 | 14:42:51 / 14:42:52 | 가장 빠른 원천 만료 14:46:50 |
| 성찰 취득 | 14:42:53 | 원래 packet 만료 14:46:53 |
| exact AI 승인 요청 기록 | 14:42:55.037 | 아직 유료 호출 없음 |
| 첫 안전 승인 대기 보고 | 14:44:06.929 | 요청 준비 후 약 72초 |
| 승인 사전검사 관측 | 14:45:40.114 | packet 잔여 약 73초 |
| 직접 승인 증거 / 정식 승인 기록 | 14:46:17.658 / 17.693 | 요청 준비부터 약 203초 |
| spent / AI 요약 기록 | 14:46:18.806 / 20.987 | generate 1, count·재시도 0 |
| REGISTER / ALLOCATE / START_REVIEW | 14:46:24 / 25 / 26 | 지급 완료가 아님 |
| 동의 가능 보고 | 14:46:33.274 | 실제 원천 잔여 약 16.7초 |
| 원천 만료 / 최종 진단 | 14:46:50 / 50.939 | 양측 동의 0, 지급 미완료 |

승인 준비부터 기록까지의 약 203초에는 에이전트 조회·보고서 생성·본부 전달·사용자 응답·승인 기록 준비가 섞여 있다. 구간별 메시지 시작·종료는 모두 보존되지 않아 사용자에게 전체 시간을 귀속할 수 없다. 첫 진단은 MANAGED_SOURCE/UNKNOWN_ERROR, 외부 진단은 NORMAL_FLOW/COLLECTION_FAILED다. 정확한 내부 예외는 저장되지 않았지만 마지막 실패 관측과 가장 빠른 원천 만료가 같은 초다. r11의 BC_VIEW_STALE를 재발 원인으로 단정하지 않는다.

## 변경된 순서와 권한

1. 별도 재시험 지시 후에만 새 호스트를 준비한다. 지갑·화면 자산·수령자·100 TEST·가격·외부전송 범위·승인 권한 지정은 짧은 원천 취득 전에 끝낸다.
2. 참여자와 운영자는 각각 로그인하고 같은 호스트의 시험 화면에서 읽기 자동 갱신을 유지한다. 두 인증된 화면의 최근 읽기가 모두 있어야 HR을 시작하고, HR이 현재 MET이며 두 화면이 준비됐을 때 성찰을 취득한다. 화면 읽기는 동의가 아니다.
3. 성찰 packet의 exact hash·모델·제한·원래 만료를 지정 승인 지갑에 표시한다. 사람이 체크하고 직접 승인해야 기존 정식 승인 파일을 만든다. 화면의 POST 자체는 모델을 호출하지 않는다. 본부 채팅 왕복을 필수 경로에서 제거했다.
4. 동일 packet의 승인된 AI 응답을 한 번 소비한 뒤 활동·과제를 한 번씩 취득한다. 마지막 네 조건이 현재 MET여야 E3로 진행한다. 성찰 acquiredAt/만료를 응답 수신시각으로 바꾸지 않는다.
5. REGISTER/ALLOCATE/START_REVIEW 뒤 두 화면은 같은 신청·판정·수령자·토큰·100 TEST를 표시한다. 각 사용자가 별도로 직접 동의한다. 새 판정에 이전 동의를 옮기지 않는다.

사전 권한 지정은 기존 native 비용·외부전송 승인자가 해당 호스트·코드 HEAD·지갑을 직접 지정했다는 증거를 private 설정에 기록하는 절차다. 참여자/운영자 역할 자체는 비용 승인 권한이 아니다. 기본값은 미지정·활성화 차단이다. 두 역할 중 어느 지갑도 명시적으로 지정할 수 있으나 이번 작업에서는 실제 지갑을 지정하지 않았다. 이 로컬 증거는 외부 청구 계정의 소유권이나 별도 신원 검증을 대신하지 않는다.

## 운영 시간 기준과 한계

| 위치 | 요구하는 남은 시간 |
| --- | --- |
| 승인 기록·모델 호출 직전 | 원래 성찰 packet 185초 이상 |
| E3 각 준비 거래 및 동의 대기 개방 전 | 원천·reviewCap 중 빠른 만료 155초 이상 |
| 각 화면의 첫 동의 가능 조회 | 조회 왕복을 보수적으로 뺀 150초 이상 |
| 새 AGREE 중단 | 잔여 30초 이하 |
| 두 화면 준비 확인 | 각각 최근 5초 이내 인증 조회 |

이는 제어시계 시나리오를 위한 데모 운영 예산이다. 원천 TTL·계약 검토 기한·지급 조건을 바꾸거나 모든 사람의 최대 검토시간·외부 API 지연을 보장하지 않는다. 첫 동의 가능 화면에서 보수적으로 120초 이상의 조작 여유를 확보하거나 중단한다. 16초를 충분한 검토시간으로 안내하지 않는다. 서버 관측시각을 타이머로 갱신하지 않고, 실제 원천 만료·조회 왕복·단조 경과시간으로 잔여시간을 줄인다.

늦은 승인은 유료 호출 전에 중단한다. 이미 승인한 모델이나 E3가 늦으면 호출 1회가 소비된 상태에서 짧은 창을 열지 않고 중단할 수 있다. 재수집·유료 자동 재시도·오래된 결과 재발급·만료 연장은 없다. 임의의 지연에서도 반드시 지급까지 완료한다는 보장은 없다.

## 경계 검토

새 exact 승인 HTTP 연결은 기존 TLS·same origin·세션·역할·CSRF를 거치며 지정 지갑, 현재 app/run/host/head, 입력·plan·context·binding·모델·가격 범위와 원래 만료를 다시 검사한다. 다른 역할·지갑·신청·입력·오래된 승인, 중복·부분 기록·spent 상태를 거부한다. 실제 원문은 표시하지 않는다. 기존 native 형식 검증·단일 소비 journal·전역 claim은 유지한다. UI 응답 미확인에는 자동 재전송하지 않는다.

새 동의 운영 제한은 기존 인증·정확한 idempotency 재생 검사 뒤, 새 명령을 기록하기 전에 적용한다. 이미 기록된 같은 키·본문의 인증된 재조회는 원래 receipt를 돌려준다. 철회는 기존 정책을 따른다. CAS·원천 현재성·양측 직접 동의·반대 의견·수령자·100 TEST·서명·지급 정책을 낮추지 않는다. SDK·암호·transport·Windows·예치 정책과 팀원의 제품 프론트는 수정하지 않았다.

오프라인 검사는 실제 SQLite/store/evaluator/procedure 및 native 승인·단일소비 코드를 사용하되 원천·모델·지갑·비용 지정 증거는 합성이다. 외부 네트워크는 차단하고 시계를 앞으로만 진행한다. 정상 120초 양측 검토, 늦은 승인·모델·화면·한쪽 동의, 정확한 경계, 원천·판정·호스트·run·가격·입력 변경, CSRF·다른 origin·중복·미확인 응답·기존 receipt 재생을 검사한다. 결과 수와 source pin은 [v22 검증](BOOTCAMP_V22_VERIFICATION.json)에 기록한다. 실제 성공의 증거가 아니다.

r5–r13, 소비된 승인·journal·전역 claim 및 과거 pin의 원래 바이트를 보존한다. 이번 개선에는 새 실제 호스트·CA·로그인·증명·외부 AI·서명·지급·merge가 없다.
