# 두 사람·두 LLM의 역할과 PR 계획

2026-10-12 제안. **오규원(A)은 백엔드·증명·계약, 서준형(B)은 화면·지갑 UX·브라우저 검증**을 먼저 맡는다. 역할은 확정 인사 배정이 아니며 첫 2~3개 PR 뒤 난이도와 선호에 맞춰 조정한다. 사람 한 명이 PR 책임자이고 LLM은 그 사람의 작업을 돕는다.

기능 목표를 Issue 단위로 설명하고, 실제 변경은 작고 독립적으로 검토 가능한 PR로 나누는 방식을 권한다. 아래 ID는 계획 ID이며 GitHub PR 번호가 아니다. 이 문서 PR은 Issue 생성·기능 구현·권한 변경을 수행하지 않는다. 실제 작업 착수 시 담당자와 의존 PR 링크를 기록한다.

## 협업 방식

- 각자 한 번에 구현 PR 하나를 맡는다. 같은 기능의 화면과 서버는 API·상태 계약을 먼저 맞추고 병렬로 진행한다. 다른 사람의 브랜치에 직접 수정하지 않는다.
- 기본 소유 범위는 [인계의 경로 표](TEAM_HANDOFF.ko.md)를 따른다. DB schema, 계약 인코딩, 공통 지갑 도구, 루트 의존성, CI 변경은 PR 설명에 다른 담당자의 영향을 적고 계약을 먼저 갱신한다.
- 변경은 최신 `origin/develop`에서 시작한다. 의존 PR이 미병합이면 합성 화면·설계까지만 독립 진행하고 실제 연결은 병합 후 한다. 장기 누적 브랜치 대신 필요한 기반을 먼저 병합한다.
- API 변경은 요청/응답·권한·실패·멱등성·상태 전이·합성 예제를 함께 정의한다. 화면은 아직 없는 API를 현재 구현으로 취급하지 않는다.
- PR 완료 기준은 담당자의 코드 리뷰, 관련 시험, 필수 CI 성공, 문서 일치다. GitHub 필수 Approve는 현재 0명이며 이 문서는 새 필수 승인을 추가하지 않는다. LLM의 병합은 사용자의 명시적 지시가 있을 때만 한다.
- 작업 종료 시 PR에 완료/미완료·검사 결과·다음 의존성을 남긴다. 대화 전문을 전달하기보다 이 문서와 해당 PR을 연결한다.

**A: C1 개발 실행 기반 / B: F0 합성 화면 골격.** 둘 다 이 문서 PR 병합 후 시작할 수 있다. F0은 실제 API가 없어도 독립 검토 가능하다. C1과 F0 병합 뒤 F1에서 실제 합성 서버와 지갑을 연결한다. A의 다음 작업은 B1이다.

C1 담당 오규원, [이슈 #10](https://github.com/gw020328-oss/clear-education-v4/issues/10): [개발 실행·프론트 연결 계약](LOCAL_SYNTHETIC.ko.md)을 따른다. F0 담당 서준형, [이슈 #11](https://github.com/gw020328-oss/clear-education-v4/issues/11): 배포용 산출물은 `web/dist`에 둔다. 정적 ES 모듈의 패키징, 해시 라우팅 및 history 기반 `/ui/` fallback, 실제 연결의 동일 origin 조건은 C1 안내를 확인한다. 병합 여부는 해당 이슈와 연결 PR에서 확인한다.

## 증명부터 지급까지

B1은 [이슈 #15](https://github.com/gw020328-oss/clear-education-v4/issues/15)로 오규원이 구현하며 [제품 세션 계약](PROOF_SESSIONS.ko.md)과 schema 3을 정의했다. 병합 상태는 연결 PR을 확인한다. 승인 nonce 소비는 proof 수락·시험 중복 예약과 구분한다. F4는 이 계약으로 화면을 준비하되 실제 수집 연결은 B2b 이후다.

나머지는 후속 구현 제안이다. 해당 API 경로·DB schema는 각 구현 PR에서 확정한다. 각 PR에서 합성 시험을 먼저 완성하며, 실제 데이터 연결은 안전한 수집·삭제 경계가 준비된 뒤 별도 실행한다.

## 모든 구현 PR에 남길 내용

계획 ID와 담당자, 사용자 관점의 변화, 포함/제외 범위, 선행 PR 링크, API·DB·서명 변경, 실제 실행한 검사, 재현 방법, 남은 제약을 적는다. 테스트 불가 사유가 있으면 통과로 대체하지 않는다. 프론트 PR은 합성 화면과 주요 실패 흐름, 백엔드 PR은 상태·동시성·복구 근거를 중심으로 검토한다.

현재 상태는 코드와 GitHub PR에서 확인하고 이 문서는 계획 변경 때 갱신한다. PR 번호를 미리 예약하거나 미래의 모든 작업을 한꺼번에 실행하도록 LLM에 지시하지 않는다.

## 참고한 협업 원칙

[GitHub Flow](https://docs.github.com/en/get-started/using-github/github-flow)의 짧은 작업 브랜치·PR 검토, [Google의 작은 변경 권장](https://google.github.io/eng-practices/review/developer/small-cls.html), [DORA의 작은 배치](https://dora.dev/capabilities/working-in-small-batches/)를 참고했다. CLEAR에서는 기존 `develop` 통합 흐름을 유지하고, 독립 검토 가능성과 DB 원자성 경계를 기준으로 PR을 나눈다. 모든 팀의 승인 정책이나 배포 방식을 그대로 복제하지 않는다.
