# 서명 대기 조회 충돌 수정 검토

2026-10-23. 검토 기준은 `18bbb2455de6971558077b4ab9a77c27008b5ba4` 이후 이번 변경이다. 권한·서명 경계의 반복 실제 실패와 원인 불확실성 때문에 사용자 지정 Astra / Xhigh 작업 단위로 진행했다. 별도 모델 중복 검토나 병렬 에이전트는 사용하지 않았다.

## 확인한 결함과 한계

실제 인증 서비스, 임시 SQLite store, UI 서명 브로커와 가짜 시계를 사용해 `getApplication`이 초 경계를 넘으면 `BC_VIEW_STALE`을 반환하는 경로를 재현했다. 수정 전 핵심 3개 검사는 조회·정기 검사·서명 제출에서 모두 pending이 영구 취소되어 실패했다. 이는 코드 결함의 결정적 재현이며, r4의 실제 최초 오류를 확정한 결과는 아니다. r4의 최초 내부 오류는 기존 기록에 없고 서버 수락은 `UNKNOWN`이다.

## 좁은 보안 검토

- 분류는 현재 pending과 신청 조회 호출 안의 정확한 `RuleError` prototype 및 own message `BC_VIEW_STALE`에만 적용한다. 인증 단계의 같은 코드, 일반 Error의 같은 문자열, SQLite/알 수 없는 오류는 보류하지 않는다. 검사할 수 없는 오류 객체도 취소한다.
- 보류 시 현재 인증·역할·CSRF·지갑과 원래 exclusive 마감을 다시 확인한다. 호출자에게 예외를 던지며 이전 조회값을 반환하지 않는다. 정기 검사는 기존 250ms 간격이며 300초/원천 만료 중 더 빠른 기존 마감이 유지된다.
- 수락은 새 성공 조회와 정확한 신청 ID·참가자·policy·mapping·ACTIVE 상태, 현재 caller 세션·chain, 원래 승인 ID·메시지·nonce 및 지갑 서명, 최종 권한/마감 재검사 뒤에만 가능하다. 보류가 수락 조건을 생략하지 않는다.
- 로그아웃·실제 세션 만료·역할 제거·신청 취소 및 바인딩 변경은 pending을 종료한다. 조회 충돌 후 진짜 권한 상실 및 조회 도중 로그아웃도 검사했다. 재사용·다른 세션/지갑/체인·잘못된 서명은 거부한다.
- store의 읽기/쓰기 전역 일관성 검사, source lease, nonce/단회성, 증명 검증, 개인정보 수명, AI 승인 및 지급 코드는 변경하지 않았다. 실패 시험에서 evidence와 절차/지급 기록은 0이며, 기존 flow 실패 검사는 AI 승인/호출/지급 진입을 차단한다.
- 진단은 최초 보류를 1회만 기록해 반복 read로 128개 상한을 소모하지 않는다. 실제 최초 실패는 별도로 보존한다. 고정 코드만 저장하고 원문 오류·stack·서명·토큰·URL/body를 보존하지 않는다. 진단 writer 실패가 권한 판정을 바꾸지 않는다.

변경 범위에서 남은 차단 수준의 보안 결함은 발견하지 않았다. 실제 로그인·원천 증명·유료 호출·지급은 이 검토에 포함하지 않았으며, 실제 재시험의 성공이나 무결함을 보장하지 않는다. 새 exact source intake와 asset manifest, 최종 HEAD의 CI 결과를 별도로 확인해야 재시험 준비를 완료한 것으로 기록한다.
