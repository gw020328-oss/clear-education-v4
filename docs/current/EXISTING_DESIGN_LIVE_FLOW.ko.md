# 기존 디자인의 단일 신청 연결

2026-11-02. 기준 develop e7f77ed(PR138). PR138 실제 100 TEST 지급은 전용 준비 화면에서 완료했으며, 기존 디자인 전체가 연결됐다는 증거는 아니었다. 그 지급 DB·체인·검증 기록은 보존한다.

## 연결한 범위

인증된 owner frame과 동일한 product session/driver/auto-reader를 유지한다. team entry가 기존 studentSection/operatorSection에 workflow를 전달하고, 같은 디자인의 CLEAR 로고·hero·band·조건 카드를 사용한다. 각 역할은 서버에 결합된 신청 한 건만 표시한다. 신청 생성→원천 세션 결합→인증서 승인 메시지 서명→AI 입력 승인→기존 V2 수령 등록→동일 판정 양측 동의→지급 영수증을 같은 디자인에서 진행한다. 예시 기수/금고 통계·충전·조건 충족 토글·가짜 로그인은 이 경로에서 사용하지 않는다.

각 단계에서 현재 필요한 동작만 노출하며, 입력 승인·등록 payload·판정 지문·영수증 JSON은 펼침 상세로 제공한다. 서명 메시지와 공개 calldata 안내는 유지한다. driver의 nonce/대상/기한/불명 결과/수동 같은 키 동의 조회·GET-only polling을 변경하지 않는다. 기한을 늘리거나 자동 서명·AI 승인·동의·POST 재시도를 추가하지 않는다.

네 조건의 기존 디자인 카드에서 현재 S4 decisionEvidence를 GET한다. 신청·역할·판정 ID/지문이 현재 view와 일치할 때만 확인 사실과 서버 부족 사유, 회고 세 항목 판정과 제공된 UTF-16 위치를 표시한다. 원문 API는 없어 텍스트나 강조 문장을 생성하지 않는다. 미제공·권한 없음·명시적 만료/삭제를 구분한다. S4의 검증 내역은 지급 권한으로 사용하지 않는다.

## 검증

프론트 회귀298개 통과. 기존 controller의 대상 변경/불명 응답/단일 동의·영수증 음성 사례를 유지하고, 역할별 기존 디자인의 실제 view/owner action 연결, S4 대상 불일치·원문 미제공/만료 구분을 추가했다. 실제 SDK --team 번들351개 자산 빌드 성공.

실제 team-entry를 사용하는 loopback HTTP와 Chrome에서 합성 신청 생성·증빙 연결·가상 메시지 서명, 별도 승인 이후 fixture에서 AI 승인·V2 등록·역할별 각1회 동의·양측 수령 표시·회고 세 항목 상세를 확인했다. 브라우저 시험의 normal client/로그인/지갑 서명/원천/AI/영수증은 시험 대역이다. 실제 제품 API의 의미와 권한 검증은 기존 normal-client/controller/제품 HTTPS 회귀 및 PR CI로 별도 검사한다. 실제 로그인·유료 AI·사용자 지급 재시험은0이다. 합성 응답을 실제 체인 지급으로 기록하지 않는다.

V57 원본을 보존하고 V58에서 네 표시 경로 변경과 네 전이 표시 의존성을 인수한다. 신규 signer/controller/API/예치 정책은 없다. 전체 PR 최종 CI는 별도 확인한다.

## 남은 범위

기수 전체 명단·금고 집계·운영 효과·정책 구조화 편집·원문 HTTP/문장 강조·다른 reviews 시나리오는 이번 단일 신청 연결의 범위 밖이다. 실제로 조회하지 않은 인원·금액을 채우지 않는다. 원천 추가 수집/이의 정정의 새 제품 경로를 임의로 확정하지 않는다. 이번 변경의 실제 사용자 재실행과 병합은 별도 승인 대상이다.

완료 화면 시각 검증에서 지급 후 대기 안내가 남는 것을 보완했다. 완료 단계는 새 동의를 제안하지 않고, 검증된 영수증 수령 상태를 표시한다. 기존 불명 동의의 같은 키 수동 결과 확인은 유지한다. 마지막 합성 완료 화면에서 수령 확인=true, 지급 대기 안내=false, 새 동의 버튼=false를 확인했다.
